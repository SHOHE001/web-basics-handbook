## 本文

### 1. データベースと DBMS

**データベース** は、データを決まった形で整理して保存し、複数の人やプログラムで共有できるようにしたものです。それを管理するソフトが **DBMS** で、PostgreSQL、MySQL、SQLite、Oracle Database などがあります。

DBMS が肩代わりしてくれる主な仕事:

- 複数の人が同時に更新しても矛盾しないようにする（**排他制御**）
- 途中で失敗しても中途半端な状態を残さない（**トランザクション管理**）
- 障害が起きても元に戻せるようにする（**障害回復**）
- 見てよい人・変えてよい人を制限する（**アクセス制御**）

**実例**: 表計算ソフトのファイルを共有フォルダに置いて何人かで同時に編集すると、「誰かの変更が消えた」が起きます。DBMS はこれを起こさないための仕組みの塊です。

### 2. 関係データベース

いま主流の **関係データベース（RDB）** は、データを **表（テーブル）** で表します。

| 学籍番号 | 氏名 | 学部コード |
|---|---|---|
| S001 | 青木 | L |
| S002 | 井上 | E |
| S003 | 上田 | L |

- 横 1 行を **行（レコード、タプル）**、縦 1 列を **列（項目、属性）** と呼ぶ
- 列ごとに入る値の種類（型）が決まっている

#### キー

| キー | 意味 |
|---|---|
| **主キー** | 行を 1 つに特定できる列（の組合せ）。<mark>**値の重複も空（NULL）も許されない**</mark> |
| **候補キー** | 主キーになれる資格を持つ列。その中から 1 つ選んだのが主キー |
| **複合キー** | 複数の列を組み合わせて初めて行を特定できるキー |
| **外部キー** | 別の表の主キーを参照する列。表と表をつなぐ |

上の表の「学部コード」が、別の「学部」表の主キーを参照していれば外部キーです。外部キーには「参照先に存在しない値は入れられない」という制約（**参照制約**）がかけられます。

**実例**: 学生証の学籍番号は、同姓同名の人がいても 1 人を特定できるので主キーに向いています。氏名は重複しうるので主キーには向きません。

### 3. 正規化

> [!CAUTION]
> 正規化は FE の例題で **初見の用語が一気に出てくる** 単元。<mark>**目的は「同じ情報を 1 か所にだけ持つ」こと**</mark> で、そうすると更新したときの食い違い（更新時異状）が起きなくなる。用語に飲まれたら、この目的に立ち返る。

次のような「注文の記録」を 1 枚の表で持っているとします。

| 注文番号 | 注文日 | 顧客番号 | 顧客名 | 商品番号 | 商品名 | 単価 | 数量 |
|---|---|---|---|---|---|---|---|
| 1001 | 11/1 | C01 | 青木 | P1 | ノート | 200 | 3 |
| 1001 | 11/1 | C01 | 青木 | P2 | ペン | 100 | 5 |
| 1002 | 11/2 | C02 | 井上 | P1 | ノート | 200 | 1 |

この表の困りごと:

- ノートの単価を変えたいとき、ノートが出てくる **すべての行** を直さないと食い違う
- まだ注文のない新商品を登録できない（注文番号がないと行を作れない）
- 注文 1002 を消すと、井上さんの顧客情報まで消える

これを分けていくのが正規化です。

#### 第 1 正規形

1 つのマスに複数の値を入れない（繰返し項目をなくす）。上の表はすでに 1 行 1 商品になっているので第 1 正規形です。

#### 第 2 正規形

この表の主キーは「注文番号 ＋ 商品番号」の組合せです。ところが「商品名・単価」は **商品番号だけ** で決まり、「注文日・顧客番号・顧客名」は **注文番号だけ** で決まります。主キーの一部だけで決まる関係（**部分関数従属**）を取り除くために、表を分けます。

- 注文（**注文番号**, 注文日, 顧客番号, 顧客名）
- 商品（**商品番号**, 商品名, 単価）
- 注文明細（**注文番号, 商品番号**, 数量）

#### 第 3 正規形

注文の表を見ると、「顧客名」は顧客番号で決まり、顧客番号は注文番号で決まります。主キー以外の列を経由して決まる関係（**推移的関数従属**）を取り除きます。

- 注文（**注文番号**, 注文日, 顧客番号）
- 顧客（**顧客番号**, 顧客名）
- 商品（**商品番号**, 商品名, 単価）
- 注文明細（**注文番号, 商品番号**, 数量）

これで、単価を変えるときは商品の表の 1 行だけ、顧客名を変えるときは顧客の表の 1 行だけ直せばよくなりました。

| 正規形 | 取り除くもの | ひとことで |
|---|---|---|
| 第 1 正規形 | 繰返し項目 | 1 マス 1 値 |
| 第 2 正規形 | 部分関数従属 | 主キーの **一部** だけで決まる列を別表へ |
| 第 3 正規形 | 推移的関数従属 | 主キー **以外** の列で決まる列を別表へ |

**関数従属** は「A が決まれば B が 1 つに決まる」関係のことで、`A → B` と書きます。学籍番号 → 氏名、のように。

### 4. E-R 図

データの構造を、**エンティティ**（実体: 顧客・注文・商品など）と **リレーションシップ**（関連）で表した図です。線の端の記号で「1 対多」などの関係を表します。

```
[顧客] 1 ──── * [注文] 1 ──── * [注文明細] * ──── 1 [商品]
```

「1 人の顧客は複数の注文をする」「1 つの注文には複数の明細がある」「1 つの商品は複数の明細に出てくる」と読みます。多対多の関係（注文と商品）は、間に表（注文明細）を挟んで 1 対多 ＋ 多対 1 に分けるのが定石です。

### 5. SQL

DBMS に命令する言語が **SQL** です。

#### データを取り出す（SELECT）

```sql
SELECT 氏名, 学部コード      -- 取り出す列（射影）
FROM 学生                     -- どの表から
WHERE 学部コード = 'L'        -- どの行を（選択）
ORDER BY 氏名 DESC;           -- 並べ方（DESC は降順、ASC は昇順）
```

#### 条件の書き方

| 書き方 | 意味 |
|---|---|
| `BETWEEN 10 AND 20` | 10 以上 20 以下 |
| `IN ('L', 'E')` | どれかに一致 |
| `LIKE '青%'` | 「青」で始まる（`%` は 0 文字以上の任意の文字列、`_` は任意の 1 文字） |
| `IS NULL` | 値が空。`= NULL` とは書かない |

#### 集計（GROUP BY と HAVING）

```sql
SELECT 学部コード, COUNT(*) AS 人数
FROM 学生
GROUP BY 学部コード          -- 学部ごとにまとめる
HAVING COUNT(*) >= 2;         -- まとめた結果に条件をつける
```

集計関数には `COUNT`（件数）、`SUM`（合計）、`AVG`（平均）、`MAX`、`MIN` があります。

<mark>**WHERE は「まとめる前の行」の条件、HAVING は「まとめた後のグループ」の条件**</mark>。集計関数を使った条件は HAVING に書きます。

#### 結合（JOIN）

複数の表を、共通の列でつないで 1 つの表のように扱います。

```sql
SELECT 注文.注文番号, 顧客.顧客名
FROM 注文
JOIN 顧客 ON 注文.顧客番号 = 顧客.顧客番号;
```

正規化でバラバラにした表を、使うときに JOIN でつなぎ直すイメージです。

#### 副問合せ

SQL の中に SQL を入れる書き方です。

```sql
-- 平均より高い商品を取り出す
SELECT 商品名 FROM 商品
WHERE 単価 > (SELECT AVG(単価) FROM 商品);
```

#### 更新系と定義系

```sql
INSERT INTO 商品 VALUES ('P3', '消しゴム', 80);   -- 追加
UPDATE 商品 SET 単価 = 220 WHERE 商品番号 = 'P1'; -- 変更
DELETE FROM 商品 WHERE 商品番号 = 'P3';          -- 削除
CREATE TABLE 商品 (...);                         -- 表を作る
```

`UPDATE` と `DELETE` で `WHERE` を書き忘れると **全行** が対象になります。

**実例**: Web 編 Ch6 の SQL インジェクションは、この `WHERE` の条件部分に、攻撃者が `' OR '1'='1' --` を差し込んで「全行が対象」に書き換える攻撃でした。

### 6. トランザクション

「ひとまとまりで成功するか、まったく行わないか」のどちらかでなければならない処理の単位が **トランザクション** です。

**実例**: 銀行振込は「A の口座から 1 万円減らす」と「B の口座に 1 万円増やす」の 2 つの更新でできています。片方だけ成功して止まると、お金が消えたり増えたりします。2 つを 1 つのトランザクションにして、両方成功したら **コミット**（確定）、途中で失敗したら **ロールバック**（取り消し）します。

#### ACID 特性

| 特性 | 意味 |
|---|---|
| **A**tomicity（原子性） | 全部やるか、全部やらないか |
| **C**onsistency（一貫性） | 処理の前後でデータの決まりごと（残高はマイナスにならない、など）が守られる |
| **I**solation（独立性） | 同時に動く他のトランザクションの影響を受けない |
| **D**urability（耐久性） | コミットした結果は、障害が起きても失われない |

#### 排他制御

複数のトランザクションが同じデータを同時に更新すると、片方の更新が消えることがあります（**ロストアップデート**）。これを防ぐために、使っている間はデータに **ロック** をかけます。

- **共有ロック**: 読む間だけかける。他の人も読めるが、書けない
- **専有ロック（排他ロック）**: 書く間にかける。他の人は読むことも書くこともできない

2 つのトランザクションがお互いの持っているロックの解除を待ち合って、どちらも進めなくなる状態を **デッドロック** と呼びます。

### 7. 障害からの回復

DBMS は更新のたびに、変更前と変更後の値を **ログファイル** に記録しています。

| 回復方法 | 使う場面 | やること |
|---|---|---|
| **ロールバック** | トランザクションの途中で失敗した | ログの **変更前** の値で元に戻す |
| **ロールフォワード** | ディスクが壊れた | バックアップから戻したあと、ログの **変更後** の値で直近まで進める |

ある時点でメモリの内容をディスクに書き出すことを **チェックポイント** と呼び、回復時はそこから処理すればよいので速くなります。

### 8. いろいろなデータベース

- **NoSQL**: 表の形にこだわらないデータベースの総称。キーバリュー型（Redis）、ドキュメント型（MongoDB）など（Web 編 Ch7）
- **ビッグデータ**: 量・種類・発生頻度が大きく、従来の方法では扱いにくいデータ
- **データウェアハウス**: 分析用に、いろいろな業務システムのデータを時系列で集めたもの
- **データマイニング**: 大量のデータから役に立つパターンを見つけること（「おむつとビールが一緒に買われる」の類）

## つまずきポイント

> [!CAUTION]
> SQL と正規化で **初学者がほぼ必ず一度は踏む** 罠のリスト。本番の DB を触るときにもそのまま効く。

- <mark>**WHERE と HAVING の違い**</mark>: まとめる前の行か、まとめた後のグループか
- <mark>**第 2 と第 3 正規形の違い**</mark>: 主キーの「一部」で決まるのが第 2、主キー「以外」の列で決まるのが第 3
- **NULL の比較は `IS NULL`**: `= NULL` は真にならない
- **ロールバックとロールフォワード**: 戻すのは変更前のログ、進めるのは変更後のログ
- **`UPDATE` / `DELETE` の WHERE 忘れ**: 全行が変わる。本番の DB で一度やると忘れない

## 重要な単語まとめ

| 用語 | 一言で言うと | 身近な実例 |
|---|---|---|
| **DBMS** | データベースを管理するソフト | PostgreSQL、SQLite |
| **関係データベース（RDB）** | 表でデータを持つデータベース | 表計算ソフトの表に近い |
| **主キー / 外部キー** | 行を特定する列 / 別の表の主キーを参照する列 | 学籍番号 / 学部コード |
| **正規化** | 同じ情報を 1 か所にだけ持つよう表を分けること | 単価を 1 行直すだけで済むようにする |
| **関数従属** | A が決まれば B が決まる関係 | 学籍番号 → 氏名 |
| **部分関数従属 / 推移的関数従属** | 主キーの一部で決まる / 主キー以外を経由して決まる | 第 2 / 第 3 正規形で取り除く |
| **E-R 図** | エンティティと関連で描くデータの設計図 | 顧客 1 対 多 注文 |
| **SELECT / WHERE / ORDER BY** | 取り出す / 条件 / 並べ替え | 検索画面の裏側 |
| **GROUP BY / HAVING** | グループにまとめる / まとめた後の条件 | 学部別の人数 |
| **JOIN** | 表どうしをつなぐ | 注文と顧客名を一緒に表示 |
| **トランザクション / コミット / ロールバック** | 一体の処理 / 確定 / 取り消し | 銀行振込 |
| **ACID 特性** | 原子性・一貫性・独立性・耐久性 | トランザクションが守るべき性質 |
| **排他制御 / デッドロック** | ロックで同時更新を防ぐ / 待ち合って止まる | 共有ファイルの同時編集 |
| **ロールフォワード** | バックアップ ＋ 変更後ログで復旧 | ディスク故障からの回復 |
