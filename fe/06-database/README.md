## 本文

### 1. データベースと DBMS

**データベース** とは、データを決まった形式で整理して保存し、複数の人やプログラムで共有できるようにした仕組みです。それを管理するソフトウェアが **DBMS** であり、PostgreSQL、MySQL、SQLite、Oracle Database などがあります。

DBMS が肩代わりしてくれる主な仕事:

- 複数の人が同時に更新しても矛盾が生じないようにする（**排他制御**）
- 処理の途中で失敗しても中途半端な状態を残さない（**トランザクション管理**）
- 障害が起きても元の状態に戻せるようにする（**障害回復**）
- 閲覧や変更ができる人を制限する（**アクセス制御**）

**実例**: 表計算ソフトのファイルを共有フォルダに置いて複数人で同時に編集すると、「誰かの変更が消えてしまう」という問題が起きます。DBMS は、こうした事態を防ぐための仕組みの集合体です。

### 2. 関係データベース

現在主流の **関係データベース（RDB）** では、データを **表（テーブル）** の形で表現します。

| 学籍番号 | 氏名 | 学部コード |
|---|---|---|
| S001 | 青木 | L |
| S002 | 井上 | E |
| S003 | 上田 | L |

- 横の 1 行を **行（レコード、タプル）**、縦の 1 列を **列（項目、属性）** と呼ぶ
- 列ごとに格納できる値の種類（型）が決まっている

#### キー

| キー | 意味 |
|---|---|
| **主キー** | 行を 1 つに特定できる列（またはその組合せ）。<mark>**値の重複も空（NULL）も許されない**</mark> |
| **候補キー** | 主キーになれる条件を満たす列。その中から 1 つ選んだものが主キーとなる |
| **複合キー** | 複数の列を組み合わせて初めて行を特定できるキー |
| **外部キー** | 別の表の主キーを参照する列。表と表をつなぐ役割を持つ |

上の表の「学部コード」が、別の「学部」表の主キーを参照していれば、これは外部キーになります。外部キーには「参照先に存在しない値は登録できない」という制約（**参照制約**）を設定できます。

**実例**: 学生証の学籍番号は、同姓同名の人がいても個人を 1 人に特定できるため主キーに向いています。一方、氏名は重複する可能性があるため主キーには向きません。

### 3. 正規化

> [!CAUTION]
> 正規化は FE の例題で **初見の用語が一気に出てくる** 単元。<mark>**目的は「同じ情報を 1 か所にだけ持つ」こと**</mark> で、そうすると更新したときの食い違い（更新時異状）が起きなくなる。用語に飲まれたら、この目的に立ち返る。

次のような「注文の記録」を 1 枚の表で管理しているとします。

| 注文番号 | 注文日 | 顧客番号 | 顧客名 | 商品番号 | 商品名 | 単価 | 数量 |
|---|---|---|---|---|---|---|---|
| 1001 | 11/1 | C01 | 青木 | P1 | ノート | 200 | 3 |
| 1001 | 11/1 | C01 | 青木 | P2 | ペン | 100 | 5 |
| 1002 | 11/2 | C02 | 井上 | P1 | ノート | 200 | 1 |

この表の困りごと:

- ノートの単価を変更したいとき、ノートが登場する **すべての行** を修正しないとデータの食い違いが生じる
- まだ注文されていない新商品を登録できない（注文番号がないと行を作成できない）
- 注文 1002 を削除すると、井上さんの顧客情報まで一緒に消えてしまう

このような問題を防ぐために表を分割していく作業が正規化です。

#### 第 1 正規形

1 つのマスに複数の値を入れないようにします（繰返し項目をなくします）。上の表はすでに 1 行につき 1 商品となっているため、第 1 正規形を満たしています。

#### 第 2 正規形

この表の主キーは「注文番号 ＋ 商品番号」の組合せです。ところが、「商品名・単価」は **商品番号だけ** で決まり、「注文日・顧客番号・顧客名」は **注文番号だけ** で決まります。このように主キーの一部だけで値が決まる関係（**部分関数従属**）を取り除くために、表を分割します。

- 注文（**注文番号**, 注文日, 顧客番号, 顧客名）
- 商品（**商品番号**, 商品名, 単価）
- 注文明細（**注文番号, 商品番号**, 数量）

#### 第 3 正規形

分割後の「注文」の表を見ると、「顧客名」は顧客番号によって決まり、その顧客番号は注文番号によって決まります。このように主キー以外の列を経由して値が決まる関係（**推移的関数従属**）を取り除きます。

- 注文（**注文番号**, 注文日, 顧客番号）
- 顧客（**顧客番号**, 顧客名）
- 商品（**商品番号**, 商品名, 単価）
- 注文明細（**注文番号, 商品番号**, 数量）

これで、単価を変更するときは「商品」の表の 1 行だけ、顧客名を変更するときは「顧客」の表の 1 行だけを修正すれば済むようになりました。

| 正規形 | 取り除くもの | ひとことで |
|---|---|---|
| 第 1 正規形 | 繰返し項目 | 1 マスに 1 値 |
| 第 2 正規形 | 部分関数従属 | 主キーの **一部** だけで決まる列を別表へ |
| 第 3 正規形 | 推移的関数従属 | 主キー **以外** の列で決まる列を別表へ |

**関数従属** とは「A が決まれば B が 1 つに決まる」という関係のことで、`A → B` と表記します。たとえば「学籍番号 → 氏名」のような関係です。

### 4. E-R 図

データの構造を、**エンティティ**（実体: 顧客・注文・商品など）と **リレーションシップ**（関連）で表現した図です。線の端にある記号で「1 対多」などの関係を表します。

```
[顧客] 1 ──── * [注文] 1 ──── * [注文明細] * ──── 1 [商品]
```

この図は「1 人の顧客は複数の注文をする」「1 つの注文には複数の明細がある」「1 つの商品は複数の明細に登場する」と読み取ります。多対多の関係（注文と商品）は、間に別の表（注文明細）を挟んで「1 対多 ＋ 多対 1」に分解するのが定石です。

### 5. SQL

DBMS に対して命令を出すための言語が **SQL** です。

#### データを取り出す（SELECT）

```sql
SELECT 氏名, 学部コード      -- 取り出す列（射影）
FROM 学生                     -- どの表から
WHERE 学部コード = 'L'        -- どの行を（選択）
ORDER BY 氏名 DESC;           -- 並べ方（DESC は降順、ASC は昇順）
```

#### 条件の書き方

| 書き方 | 意味 |
|---|---|
| `BETWEEN 10 AND 20` | 10 以上 20 以下 |
| `IN ('L', 'E')` | いずれかに一致 |
| `LIKE '青%'` | 「青」で始まる（`%` は 0 文字以上の任意の文字列、`_` は任意の 1 文字） |
| `IS NULL` | 値が空である。`= NULL` とは書かない |

#### 集計（GROUP BY と HAVING）

```sql
SELECT 学部コード, COUNT(*) AS 人数
FROM 学生
GROUP BY 学部コード          -- 学部ごとにまとめる
HAVING COUNT(*) >= 2;         -- まとめた結果に条件をつける
```

集計関数には、`COUNT`（件数）、`SUM`（合計）、`AVG`（平均）、`MAX`、`MIN` があります。

<mark>**WHERE は「まとめる前の行」に対する条件、HAVING は「まとめた後のグループ」に対する条件**</mark>を指定します。集計関数を使った条件は HAVING に記述します。

#### 結合（JOIN）

複数の表を共通の列でつなぎ合わせ、1 つの表のように扱います。

```sql
SELECT 注文.注文番号, 顧客.顧客名
FROM 注文
JOIN 顧客 ON 注文.顧客番号 = 顧客.顧客番号;
```

正規化によって分割した表を、データを利用するときに JOIN でつなぎ直すイメージです。

#### 副問合せ

SQL の中に別の SQL を埋め込む書き方です。

```sql
-- 平均より高い商品を取り出す
SELECT 商品名 FROM 商品
WHERE 単価 > (SELECT AVG(単価) FROM 商品);
```

#### 更新系と定義系

```sql
INSERT INTO 商品 VALUES ('P3', '消しゴム', 80);   -- 追加
UPDATE 商品 SET 単価 = 220 WHERE 商品番号 = 'P1'; -- 変更
DELETE FROM 商品 WHERE 商品番号 = 'P3';          -- 削除
CREATE TABLE 商品 (...);                         -- 表を作る
```

`UPDATE` と `DELETE` で `WHERE` を書き忘れると、表の **全行** が処理の対象になってしまいます。

**実例**: Web 編 Ch6 で扱った SQL インジェクションは、この `WHERE` の条件部分に攻撃者が `' OR '1'='1' --` を差し込み、「全行が対象」になるよう書き換える攻撃でした。

### 6. トランザクション

「ひとまとまりの処理としてすべて成功するか、あるいはまったく行わないか」のどちらかでなければならない処理の単位を **トランザクション** と呼びます。

**実例**: 銀行振込は、「A の口座から 1 万円を減らす」処理と「B の口座に 1 万円を増やす」処理の 2 つの更新で成り立っています。片方だけ成功して処理が止まってしまうと、お金が消えたり増えたりする矛盾が生じます。そこで、この 2 つを 1 つのトランザクションとしてまとめ、両方とも成功したら **コミット**（確定）し、途中で失敗したら **ロールバック**（取り消し）します。

#### ACID 特性

| 特性 | 意味 |
|---|---|
| **A**tomicity（原子性） | すべて実行されるか、まったく実行されないかのどちらかである |
| **C**onsistency（一貫性） | 処理の前後でデータの整合性（残高はマイナスにならない、など）が保たれる |
| **I**solation（独立性） | 同時に実行されている他のトランザクションから影響を受けない |
| **D**urability（耐久性） | いったんコミットした結果は、その後に障害が起きても失われない |

#### 排他制御

複数のトランザクションが同じデータを同時に更新すると、片方の更新内容が上書きされて消えてしまうことがあります（**ロストアップデート**）。これを防ぐため、データを使用している間は **ロック** をかけます。

- **共有ロック**: データを読み取る間だけかける。他の人も読み取ることはできるが、書き込むことはできない
- **専有ロック（排他ロック）**: データを書き込む間にかける。他の人は読み取ることも書き込むこともできない

2 つのトランザクションがお互いに相手のロック解除を待ち続け、どちらも処理を進められなくなる状態を **デッドロック** と呼びます。

### 7. 障害からの回復

DBMS はデータを更新するたびに、変更前と変更後の値を **ログファイル** に記録しています。

| 回復方法 | 使う場面 | やること |
|---|---|---|
| **ロールバック** | トランザクションの途中で失敗したとき | ログの **変更前** の値を使って元の状態に戻す |
| **ロールフォワード** | ディスクが破損したとき | バックアップから復元したあと、ログの **変更後** の値を使って障害発生直前の状態まで進める |

ある時点でメモリ上の内容をディスクに書き出す処理を **チェックポイント** と呼びます。障害からの回復時には、このチェックポイントから処理を再開すればよいため、復旧時間を短縮できます。

### 8. いろいろなデータベース

- **NoSQL**: 表の形式にとらわれないデータベースの総称。キーバリュー型（Redis）やドキュメント型（MongoDB）などがある（Web 編 Ch7）
- **ビッグデータ**: 量・種類・発生頻度が非常に大きく、従来の方法では扱いにくいデータ
- **データウェアハウス**: 分析を目的として、さまざまな業務システムのデータを時系列に集約したもの
- **データマイニング**: 大量のデータから有益なパターンを見つけ出す手法（「おむつとビールが一緒に買われやすい」といった傾向の発見など）

## つまずきポイント

> [!CAUTION]
> SQL と正規化で **初学者がほぼ必ず一度は踏む** 罠のリスト。本番の DB を触るときにもそのまま効く。

- <mark>**WHERE と HAVING の違い**</mark>: まとめる前の行に対する条件か、まとめた後のグループに対する条件か
- <mark>**第 2 と第 3 正規形の違い**</mark>: 主キーの「一部」によって決まるのが第 2 正規形、主キー「以外」の列によって決まるのが第 3 正規形
- **NULL の比較は `IS NULL`**: `= NULL` と書いても真（true）にはならない
- **ロールバックとロールフォワード**: 元に戻すときは変更前のログを使い、前に進めるときは変更後のログを使う
- **`UPDATE` / `DELETE` の WHERE 忘れ**: 全行が書き換わってしまう。本番の DB で一度経験すると二度と忘れない

## 重要な単語まとめ

| 用語 | 一言で言うと | 身近な実例 |
|---|---|---|
| **DBMS** | データベースを管理するソフト | PostgreSQL、SQLite |
| **関係データベース（RDB）** | 表の形式でデータを持つデータベース | 表計算ソフトのシートに近い |
| **主キー / 外部キー** | 行を特定する列 / 別の表の主キーを参照する列 | 学籍番号 / 学部コード |
| **正規化** | 同じ情報を 1 か所にだけ持つように表を分けること | 単価を 1 行直すだけで済むようにする |
| **関数従属** | A が決まれば B が決まる関係 | 学籍番号 → 氏名 |
| **部分関数従属 / 推移的関数従属** | 主キーの一部で決まる / 主キー以外を経由して決まる | 第 2 / 第 3 正規形で取り除く |
| **E-R 図** | エンティティと関連で描くデータの設計図 | 顧客 1 対 多 注文 |
| **SELECT / WHERE / ORDER BY** | 取り出す / 条件指定 / 並べ替え | 検索画面の裏側の処理 |
| **GROUP BY / HAVING** | グループにまとめる / まとめた後の条件指定 | 学部別の人数集計 |
| **JOIN** | 表どうしをつなぐ | 注文と顧客名を一緒に表示する |
| **トランザクション / コミット / ロールバック** | 一連のまとまった処理 / 確定 / 取り消し | 銀行振込の処理 |
| **ACID 特性** | 原子性・一貫性・独立性・耐久性 | トランザクションが守るべき性質 |
| **排他制御 / デッドロック** | ロックで同時更新を防ぐ / お互いに待ち合って止まる | 共有ファイルの同時編集 |
| **ロールフォワード** | バックアップ ＋ 変更後ログで復旧する | ディスク故障からの回復 |
