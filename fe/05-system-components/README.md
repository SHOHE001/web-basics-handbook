## 本文

### 1. 処理形態

| 形態 | 中身 | 身近な例 |
|---|---|---|
| **集中処理** | 1 台の大型コンピュータでまとめて処理する | 昔の銀行の勘定系システム |
| **分散処理** | 複数のコンピュータで分担して処理する | Web サービス全般 |
| **クライアントサーバシステム** | 依頼する側（クライアント）と提供する側（サーバ）に役割を分ける | ブラウザと Web サーバー（Web 編 Ch1） |
| **3 層クライアントサーバ** | 表示（プレゼンテーション層）・処理（ファンクション層）・データ（データ層）の 3 つに分ける | ブラウザ ＋ FastAPI ＋ PostgreSQL |
| **P2P（ピアツーピア）** | 対等な端末どうしが直接やり取りする | ファイル共有、一部のオンラインゲーム |

**実例**: Web 編 Ch5〜7 で作った構成（ブラウザの HTML → FastAPI の API → DB）は、まさに 3 層クライアントサーバシステムです。

#### 処理のタイミング

- **バッチ処理**: データをためておき、まとめて処理する（毎月の給与計算、夜間の集計）
- **リアルタイム処理**: 発生したらすぐに処理する（電車の座席予約、ATM）
- **対話型処理**: 利用者と画面でやり取りしながら処理を進める

### 2. 止まらないシステムの構成

#### 2 台で組む方式

| 方式 | 中身 | 特徴 |
|---|---|---|
| **デュアルシステム** | 2 台で **同じ処理を同時に** 実行し、結果を照合する | 故障にすぐ気付ける。信頼性は高いがコストも高い |
| **デュプレックスシステム** | 1 台が本番（主系）、もう 1 台は待機（従系）とし、主系が壊れたら切り替える | 切替えに時間がかかることがある |

デュプレックスシステムの待機のさせ方:

- **ホットスタンバイ**: 待機側もすぐ動ける状態で起動しておく。切替えが速い
- **コールドスタンバイ**: 待機側は止めておき、障害時に起動する。安いが切替えが遅い

#### クラスタとロードバランシング

複数台のコンピュータをまとめて 1 つのシステムのように扱う構成を **クラスタ** と呼びます。処理を振り分ける装置が **ロードバランサ**（Web 編 Ch7）です。台数を増やして性能を上げることを **スケールアウト**、1 台のコンピュータを高性能にすることを **スケールアップ** といいます。

#### RAID

複数のディスクを組み合わせて、速さや信頼性を高める技術です。

| RAID | 方式 | 1 台壊れたら |
|---|---|---|
| **RAID 0** | **ストライピング**: データを分けて複数のディスクに同時に書き込む。速い | データが失われる（冗長性なし） |
| **RAID 1** | **ミラーリング**: 同じデータを 2 台に書き込む | もう 1 台で動き続ける。容量は半分になる |
| **RAID 5** | ストライピング ＋ **パリティ**（誤り訂正用の情報）を分散して書き込む。3 台以上必要 | パリティから復元できる |
| **RAID 6** | パリティを 2 種類持つ | 2 台同時に壊れても復元できる |

> [!CAUTION]
> <mark>**RAID 0 には冗長性がない**</mark>（速くなるだけで、1 台でも壊れたらすべてのデータが失われる）。「RAID ＝ 安全」と覚えていると引っかかりやすい。また、RAID はあくまで「ディスクの故障」への備えであり、誤って消したファイルやランサムウェアによる被害には効果がない。**RAID はバックアップの代わりにはならない**。

### 3. 仮想化とクラウド

#### 仮想化

1 台の物理的なコンピュータの上で、ソフトウェアによって複数のコンピュータを動かす技術です。

- **仮想マシン（VM）**: OS ごと丸ごと仮想化する。1 台のコンピュータ上で Windows と Linux を同時に動かせる
- **コンテナ**: OS の中心部分（カーネル）は共有し、アプリと必要なライブラリだけを箱に詰めて動かす。VM より軽くて起動が速い（Docker など）
- **ライブマイグレーション**: VM を動かしたまま別の物理サーバへ移す

#### クラウドのサービスモデル

| モデル | 利用者が用意するもの | 例 |
|---|---|---|
| **IaaS** | OS から上の部分すべて | AWS EC2 |
| **PaaS** | アプリのコードとデータ | Render、Heroku |
| **SaaS** | 何も作らず、完成したソフトを使う | Gmail、Notion、Slack |

Web 編 Ch7 で Render（PaaS）を使って API をデプロイした手順は、この表の真ん中にあたります。

#### そのほかの形態

- **オンプレミス**: 自社で機器を所有して運用する
- **ハウジング**: 自社の機器を事業者の施設（データセンター）に置かせてもらう
- **ホスティング**: 事業者の機器を借りて使う
- **エッジコンピューティング**: 利用者に近い場所で処理を行い、遅延を減らす

### 4. 性能の評価

| 指標 | 意味 |
|---|---|
| **スループット** | 単位時間あたりに処理できる仕事の量 |
| **レスポンスタイム（応答時間）** | 要求を出してから、最初の応答が返り始めるまでの時間 |
| **ターンアラウンドタイム** | 要求を出してから、結果がすべて返ってくるまでの時間 |

**実例**: ブラウザでページを開いたとき、最初の文字が表示されるまでがレスポンスタイム、画像まで含めてすべて表示し終わるまでがターンアラウンドタイムのイメージです。Web 編 Ch1 で開いた開発者ツールの Network タブにある「Waterfall」で実際の時間を確認できます。

性能の測り方としては、標準的なプログラムを実行して性能を比べる **ベンチマーク** や、実際に近い負荷をかけて限界を調べる **負荷テスト** があります。

### 5. 信頼性の指標

#### RASIS

システムの評価項目の頭文字を並べたものです。

| 項目 | 意味 |
|---|---|
| **R**eliability（信頼性） | 壊れにくさ |
| **A**vailability（可用性） | 使いたいときに使えること |
| **S**erviceability（保守性） | 直しやすさ |
| **I**ntegrity（保全性・完全性） | データが矛盾なく正しいこと |
| **S**ecurity（安全性・機密性） | 不正から守られていること |

#### MTBF・MTTR・稼働率

- **MTBF**（平均故障間隔）: 故障してから次に故障するまでの、稼働している時間の平均。**長いほど信頼性が高い**
- **MTTR**（平均修理時間）: 故障してから復旧するまでの時間の平均。**短いほど保守性が高い**

```
稼働率 ＝ MTBF ÷ (MTBF ＋ MTTR)
```

**例題**: MTBF が 990 時間、MTTR が 10 時間なら、稼働率 ＝ 990 ÷ 1,000 ＝ **0.99**（99%）。

#### 直列と並列の稼働率

> [!CAUTION]
> <mark>**直列は「全部動いて初めて動く」、並列は「どれか 1 つでも動けば動く」**</mark>。並列の式を直列と同じ掛け算にしてしまうミスが定番である。並列は「全部止まる確率」を 1 から引く、と覚える。

```
直列（A と B の両方が必要）:  稼働率 ＝ A × B
並列（A か B のどちらかでよい）: 稼働率 ＝ 1 − (1 − A) × (1 − B)
```

**例題**: 稼働率 0.9 の装置を 2 台つなぐ場合

- 直列なら 0.9 × 0.9 ＝ **0.81**（1 台のときより下がる）
- 並列なら 1 − 0.1 × 0.1 ＝ **0.99**（1 台のときより上がる）

**実例**: Web 編 Ch7 の構成で、ロードバランサの裏にアプリサーバを 2 台並べるのは、「並列」にして稼働率を上げる工夫です。一方、「LB → アプリ → DB」と縦につながっている部分は直列なので、どこか 1 つでも止まれば全体が止まります。そのため、DB もプライマリ ＋ レプリカの構成にして並列にします。

#### バスタブ曲線

機器の故障率は時間の経過とともに、①初期故障期（製造不良で故障が多い）→ ②偶発故障期（故障率が低く安定している）→ ③摩耗故障期（経年劣化で故障が増える）と変化し、グラフが浴槽（バスタブ）の断面のような形になります。

### 6. 信頼性を高める設計

| 考え方 | 意味 | 身近な例 |
|---|---|---|
| **フォールトトレランス** | 故障が起きても機能を維持する | RAID 1、二重化した電源 |
| **フェールセーフ** | 故障したら **安全な側** に倒れて止まる | 停電すると赤信号で止まる踏切、倒れると消える石油ストーブ |
| **フェールソフト** | 故障した部分を切り離し、機能を落としてでも動き続ける | エンジンが 1 基停止しても飛べる飛行機 |
| **フールプルーフ** | 人が間違えても危険が起きないようにする | ドアが閉まらないと動かない電子レンジ、向きを間違えて挿せないコネクタ |
| **フォールトアボイダンス** | そもそも故障しないよう、品質の高い部品を使う | 高信頼の部品選定 |

### 7. 費用の考え方

**TCO**（総所有コスト）は、システムの購入費用（初期費用）だけでなく、運用・保守・電気代・教育などの **ランニングコストまで含めた総額** です。クラウドは初期費用が安い代わりに、使い続けるほど費用がかかる、という比較でよく登場します。

## 手を動かすパート

稼働率の計算は Python で確かめると手早く行えます。

```python
>>> a = 0.9
>>> a * a                    # 直列
0.81
>>> 1 - (1 - a) * (1 - a)    # 並列
0.99
>>> 990 / (990 + 10)         # MTBF と MTTR から
0.99
```

直列と並列が混ざった複雑な構成は、**内側の並列部分を 1 つの装置とみなして稼働率を出してから、外側の直列を計算する** という順番で解きます。

## つまずきポイント

> [!CAUTION]
> 稼働率と冗長化の問題で **計算の型を取り違える** 罠のリスト。式を丸暗記するより「全部動く必要があるか、どれか 1 つ動けばよいか」で考える。

- <mark>**並列の稼働率は 1 − (止まる確率の積)**</mark>: 直列と同じ掛け算にしない
- <mark>**RAID 0 は冗長性なし**</mark>: 速くするためだけの方式。RAID 1 は容量が半分になる
- <mark>**デュアルとデュプレックス**</mark>: 同時に動かして照合するのがデュアル、片方を待機させておくのがデュプレックス
- **フェールセーフとフェールソフト**: 安全に止まるのがセーフ、機能を落として動き続けるのがソフト
- **レスポンスタイムとターンアラウンドタイム**: 「最初の応答が返るまで」か「すべて終わるまで」か
