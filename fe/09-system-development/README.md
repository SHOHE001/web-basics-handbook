## 本文

### 1. 開発の流れ

システム開発は、だいたい次の順で進みます。

```
企画 → 要件定義 → 設計（外部設計・内部設計）→ 実装（プログラミング）
     → テスト → 導入・受入れ → 運用・保守
```

発注する側と受注する側で「どの作業をどこまでやるか」の認識がずれないよう、作業の範囲と用語を共通にしたガイドラインが **共通フレーム**（SLCP-JCF）です。

### 2. 要件定義

利用者が「何をしたいのか」を明らかにして、システムに求めることを決める工程です。

| 種類 | 意味 | 例（学食の注文アプリ） |
|---|---|---|
| **機能要件** | システムが **何をするか** | メニューを表示する、注文を受け付ける、学生証で決済する |
| **非機能要件** | **どのくらいの品質で** するか（性能・信頼性・使いやすさ・セキュリティなど） | 昼休みの 500 人同時アクセスで 2 秒以内に応答する、稼働率 99.5% |

<mark>**非機能要件は「言われないと漏れやすい」**</mark> ので、要件定義で意識して聞き出します。Web 編 Ch7 の「100 ユーザーは別の話」は非機能要件の話です。

要件を整理する手法として、業務の流れを図にする **DFD**（データの流れ図）や、利用者とシステムのやり取りを表す **ユースケース図**、試作品を見せて意見をもらう **プロトタイピング** があります。

### 3. 設計

- **外部設計**: 利用者から見える部分の設計。画面・帳票・操作の流れ、外部とのやり取り
- **内部設計**: 開発者から見える部分の設計。プログラムの分け方、データの持ち方、処理の手順

#### モジュール分割の良し悪し

プログラムを部品（**モジュール**）に分けるとき、良い分け方の基準が 2 つあります。

> [!CAUTION]
> <mark>**良い設計は「モジュール強度（凝集度）は強く、モジュール結合度は弱く」**</mark>。1 つの部品の中身はまとまっていて（強度が強い）、部品どうしは互いのことをあまり知らない（結合度が弱い）のが理想。「どちらも強い方がいい」と思い込むと逆を選んでしまう。

- **モジュール強度（凝集度）**: 1 つのモジュールの中の処理が、どれだけ 1 つの目的にまとまっているか。最も強いのは **機能的強度**（1 つの機能だけを持つ）、最も弱いのは **暗合的強度**（無関係な処理の寄せ集め）
- **モジュール結合度**: モジュールどうしがどれだけ依存しあっているか。最も弱い（良い）のは **データ結合**（必要なデータだけを引数で渡す）、最も強い（悪い）のは **内容結合**（他のモジュールの内部を直接いじる）

**実例**: Web 編 Ch5 の FastAPI で、1 つのエンドポイント（関数）が「1 つの操作だけ」をし、必要な値を引数で受け取っているのは、強度が強く結合度が弱い良い分け方です。逆に、何でもする巨大な関数があちこちの共通変数（グローバル変数）を書き換える作りは、直すたびに別の場所が壊れます。

### 4. オブジェクト指向

データと、そのデータを扱う処理をひとまとめにして考える方法です。

| 用語 | 意味 | たとえ |
|---|---|---|
| **クラス** | オブジェクトの設計図 | たい焼きの型 |
| **インスタンス** | クラスから作った実物 | 焼き上がったたい焼き 1 つ 1 つ |
| **カプセル化** | データを外から直接触らせず、決まった操作（メソッド）からだけ扱わせる | 自販機の中身には触れず、ボタンでだけ買える |
| **継承** | 親クラスの性質を子クラスが受け継ぎ、差分だけ書く | 「乗り物」を受け継いだ「自転車」「電車」 |
| **ポリモーフィズム（多相性）** | 同じ命令でも、受け取ったオブジェクトによってふるまいが変わる | 「鳴け」と言うと、犬はワン、猫はニャー |

- **汎化 / 特化**: 共通部分を取り出して親にまとめるのが汎化、親から具体的な子を作るのが特化（「is-a」の関係: 自転車 is a 乗り物）
- **集約 / 分解**: 部品を組み合わせて全体を作る関係（「part-of」の関係: タイヤ is part of 自転車）

#### UML

オブジェクト指向の設計を図で表すための共通の書き方です。

| 図 | 表すもの |
|---|---|
| **クラス図** | クラスと、クラスどうしの関係 |
| **ユースケース図** | 利用者（アクター）がシステムで何をするか |
| **シーケンス図** | オブジェクトどうしのやり取りを時間の順に |
| **アクティビティ図** | 処理の流れ（流れ図に近い） |
| **ステートマシン図** | 状態と、その移り変わり |

### 5. テスト

#### テストの段階

| テスト | 確かめること | 対応する工程 |
|---|---|---|
| **単体テスト** | モジュール 1 つ 1 つが正しく動くか | 内部設計 |
| **結合テスト** | モジュールを組み合わせて正しく連携するか | 外部設計 |
| **システムテスト** | システム全体が要件どおりか（性能などの非機能要件も） | 要件定義 |
| **運用テスト / 受入れテスト** | 利用者が実際の業務で使えるか（発注側が行う） | 企画・要件 |
| **回帰テスト（リグレッションテスト）** | 修正したことで、ほかの場所が壊れていないか | 変更のたびに |

結合テストで、まだできていない下位のモジュールの代わりに置く仮の部品を **スタブ**、上位のモジュールの代わりに呼び出す仮の部品を **ドライバ** と呼びます。

#### テストケースの作り方

**ブラックボックステスト**: プログラムの中身は見ずに、入力と出力の関係（仕様）だけでテストする。

- **同値分割**: 入力を「同じ扱いになるグループ」に分け、各グループから代表値を 1 つずつ選ぶ
- **境界値分析**: グループの **境目の値** を重点的にテストする。バグは境目に集まりやすいから

**例**: 「18 歳以上 65 歳未満は一般料金、それ以外は割引」という仕様なら

- 同値分割: 「18 未満」「18 以上 65 未満」「65 以上」から代表値（10、30、70 など）
- 境界値分析: 17、18、64、65 を必ずテストする

**ホワイトボックステスト**: プログラムの中身（処理の流れ）を見て、どの道筋を通るかを基準にテストする。

| 網羅の基準 | 満たす条件 |
|---|---|
| **命令網羅** | すべての命令を少なくとも 1 回実行する |
| **判定条件網羅（分岐網羅）** | すべての分岐の「真」と「偽」を少なくとも 1 回ずつ通る |
| **条件網羅** | 判定の中の個々の条件の「真」と「偽」を少なくとも 1 回ずつとる |
| **複数条件網羅** | 個々の条件の真偽の **すべての組合せ** を試す |

#### レビュー

テストの前に、設計書やプログラムを人の目で確かめるのが **レビュー** です。作った人が説明して参加者が指摘する **ウォークスルー**、役割を決めて公式に行う **インスペクション** などがあります。

### 6. 開発手法

| 手法 | 進め方 | 向いている場面 |
|---|---|---|
| **ウォーターフォール** | 工程を上から順に進め、原則として前に戻らない | 要件がはっきり決まっている大規模開発 |
| **プロトタイピング** | 早い段階で試作品を作って、利用者の意見で要件を固める | 画面の使い勝手が大事なとき |
| **スパイラルモデル** | 設計・試作・評価をくり返して、少しずつ大きくする | リスクの大きい開発 |
| **アジャイル** | 短い期間（1〜4 週間ほど）で「動くもの」を作っては見直す、をくり返す | 要件が変わりやすいとき |

#### アジャイルの代表的な手法

- **スクラム**: 短い開発期間（**スプリント**）をくり返す。やることの一覧（プロダクトバックログ）を優先度順に並べ、毎日短い打ち合わせ（デイリースクラム）をする
- **XP（エクストリームプログラミング）**: 具体的な実践の集まり
  - **ペアプログラミング**: 2 人 1 組で 1 台に向かい、1 人が書き、もう 1 人が確認する
  - **テスト駆動開発（TDD）**: 先にテストを書き、それを通すコードを書く
  - **リファクタリング**: 外から見た動きは変えずに、中の作りを分かりやすく直す
  - **継続的インテグレーション（CI）**: 変更をこまめに統合し、そのたびに自動でテストする

#### DevOps

開発（Development）と運用（Operations）が協力して、変更を速く安全に本番へ届ける考え方です。**CI/CD**（Web 編 Ch7）でテストとデプロイを自動化するのが中心です。

**実例**: このハンドブック自体も、変更をブランチで作ってプルリクエストでまとめる、という小さな開発サイクルで書かれています。

### 7. 保守と、開発を支える技術

- **保守**: 運用開始後の修正。不具合の **是正保守**、環境の変化への対応の **適応保守**、将来の問題を前もって防ぐ **予防保守** など
- **リバースエンジニアリング**: 既存のプログラムを解析して、仕様や設計を明らかにする
- **バージョン管理**: ファイルの変更履歴を管理する（Git など）
- **ソフトウェアの再利用**: 部品やライブラリを使い回して、開発を速く・品質を安定させる

## 手を動かすパート

境界値分析を Python のテストで書くと、こうなります。`assert` は「この条件が真でなければエラーにする」命令です。

```python
def fee(age: int) -> str:
    if 18 <= age < 65:
        return "一般"
    return "割引"

# 境界値をテストする
assert fee(17) == "割引"
assert fee(18) == "一般"
assert fee(64) == "一般"
assert fee(65) == "割引"
print("すべての境界値テストに合格")
```

条件を `18 < age` に書き間違えると `fee(18)` のテストで止まります。境目を試す意味を体感してください。

## つまずきポイント

> [!CAUTION]
> 開発技術は **似た名前の対になる用語** を入れ替えた選択肢が多い。対で覚える。

- <mark>**強度は強く、結合度は弱く**</mark>: 「どちらも強い（弱い）方がいい」ではない
- <mark>**同値分割と境界値分析**</mark>: 代表値を選ぶのが同値分割、境目を狙うのが境界値分析
- <mark>**判定条件網羅と条件網羅**</mark>: 分岐の真偽か、個々の条件の真偽か
- **スタブとドライバ**: 下位の代わりがスタブ、上位の代わりがドライバ
- **受入れテストは発注側が行う**: 開発側のテストではない
