## 本文

### 1. OWASP Top 10

**OWASP** は、Web アプリケーションのセキュリティに取り組む国際的なコミュニティです。重大なリスクの上位 10 種類をまとめた **OWASP Top 10** を数年ごとに改訂していて、どの改訂でも、<mark>**アクセス制御（認可）の不備とインジェクションは上位の常連**</mark> です。試験でも実務でも、対策の抜けを確かめるチェックリストとしてよく使われます。

### 2. XSS の深掘り

#### 3 つの型

| 型 | 攻撃の文字列がどこから来るか |
|---|---|
| **反射型** | 利用者が踏んだ URL の中。サーバがそれをそのまま画面に出す |
| **格納型（持続型）** | 掲示板の投稿などとしてサーバに保存され、見た人全員に出る（Web 編 Ch6 の例） |
| **DOM ベース** | サーバを通らず、ブラウザの JavaScript が URL の `#` 以降などを読んで画面に書き込む |

DOM ベース XSS は、サーバ側のエスケープでは防げません。Web 編 Ch2 で見たとおり、`#` 以降（フラグメント）は **サーバに送られない** からです。対策は、JavaScript で画面に書き込むときに `innerHTML` を避けて `textContent` を使うこと（Web 編 Ch6）です。

#### 出力の文脈ごとのエスケープ

> [!CAUTION]
> <mark>**エスケープの方法は、値を埋め込む場所（文脈）によって違う**</mark>。HTML の本文なら `<` `>` `&` `"` `'` を実体参照に、属性値なら必ず引用符で囲んだうえでエスケープ、JavaScript の文字列の中なら JavaScript 用のエスケープ、URL なら URL エンコード。さらに `href` 属性に `javascript:` で始まる URL を入れさせない。「HTML エスケープしたから安全」は、文脈が違えば成り立たない。

### 3. 認可の不備

ログインはできていても、**「この人がこのデータを見てよいか」** の確認が抜けている不備です。

**例**: 注文の詳細を `GET /orders/1001` で表示する API で、URL の番号を `1002` に変えると、他人の注文が見えてしまう。サーバが「注文 1002 の持ち主はログイン中の利用者か」を確かめていないのが原因です（**IDOR**: 安全でない直接オブジェクト参照）。

- **対策**: すべての API で、サーバ側で利用者とデータの持ち主を照合する。画面にボタンを出さないだけでは、URL や API を直接呼ばれると防げない
- **権限の昇格**: 一般の利用者が、管理者向けの API を直接呼べてしまう。管理者向けの機能も、サーバ側で役割を確かめる

Web 編 Ch6 の「認証と認可は別物」が、ここで具体的な脆弱性になります。

### 4. セッション管理の不備

| 不備 | 中身 | 対策 |
|---|---|---|
| **セッション ID の推測** | 連番や時刻から ID を推測される | 十分に長い乱数で作る |
| **セッションの固定化** | 攻撃者が用意したセッション ID のまま被害者にログインさせ、そのセッションを乗っ取る | <mark>**ログインに成功したら、セッション ID を新しく作り直す**</mark> |
| **セッション ID の漏えい** | URL に含めて、Referer やログから漏れる | Cookie で受け渡し、`Secure`・`HttpOnly` を付ける |
| **ログアウトしても有効なまま** | サーバ側でセッションを破棄していない | ログアウト時にサーバ側で無効化、一定時間で期限切れ |

### 5. そのほかの代表的な脆弱性

- **SSRF**（サーバサイドリクエストフォージェリ）: 「この URL の画像を取り込む」のような機能に、外からは届かない社内のアドレスやクラウドの管理用アドレス（インスタンスのメタデータ）を指定させ、サーバ自身に内部へアクセスさせる。対策は、接続先を許可した一覧に限ること、内部のアドレスへの接続を拒否すること
- **OS コマンドインジェクション**: 入力をそのまま OS のコマンドに組み込み、`; rm -rf ...` のような別のコマンドを実行される。シェルを経由せず、引数を分けて渡す API を使う
- **パストラバーサル**: ファイル名の入力に `../` を含めて、公開していないファイルを読む。ファイル名をそのまま使わず、決まった一覧から選ばせる
- **安全でないデシリアライズ**: 外から受け取ったデータを、プログラムのオブジェクトに戻すときに、任意のコードを実行させられる。信頼できないデータには、JSON のような単純な形式を使う
- **オープンリダイレクト**: `?next=` のようなリダイレクト先の指定を悪用され、正規のサイトを経由して偽サイトに誘導される

### 6. ブラウザ側の防御

| 仕組み | 役割 |
|---|---|
| **CSP**（Content Security Policy） | ページで実行してよいスクリプトの出どころを、レスポンスヘッダで宣言する。XSS が起きても被害を抑える |
| **HSTS** | 「このサイトには今後 HTTPS でしか接続しない」とブラウザに覚えさせ、HTTP への格下げを防ぐ |
| **Cookie の属性** | `Secure`・`HttpOnly`・`SameSite`（Web 編 Ch3・Ch6）。`__Host-` で始まる名前の Cookie は、HTTPS・ドメインの指定なし・パス `/` を強制できる |
| **X-Frame-Options / frame-ancestors** | 他のサイトに `iframe` で埋め込まれるのを防ぐ（クリックジャッキング対策） |
| **CORS の正しい設定** | 許可するオリジンを明示する（Web 編 Ch5）。リクエストの `Origin` をそのまま `Access-Control-Allow-Origin` に返し、しかも Cookie 付きを許す設定は、どのサイトからでもデータを読めてしまう誤り |

## 手を動かすパート

Web 編 Ch5 の `chapters/05-web-app/code/app.py` を起動して、ブラウザの開発者ツールの Network タブで、レスポンスヘッダに何が付いているかを見てください。CSP や HSTS が付いていないことが分かります。

```powershell
cd chapters\05-web-app\code
uvicorn app:app --reload
```

さらに、ヘッダを付ける練習として、`app.py` に次のようなミドルウェアを足すと、すべてのレスポンスにヘッダが付きます（学習用。HSTS は HTTPS で配信するときにだけ意味を持つ）。

```python
@app.middleware("http")
async def security_headers(request, call_next):
    response = await call_next(request)
    response.headers["Content-Security-Policy"] = "default-src 'self'"
    response.headers["X-Content-Type-Options"] = "nosniff"
    response.headers["X-Frame-Options"] = "DENY"
    return response
```

このヘッダを付けた状態で `http://127.0.0.1:8000/docs` を開くと、Swagger UI の画面が表示されなくなります。Swagger UI は `cdn.jsdelivr.net` からスクリプトを読み込んでいて、`default-src 'self'`（同じオリジン以外からの読み込みを禁止）に引っかかるからです。開発者ツールのコンソールに出る CSP 違反のエラーで、何が止められたかを確かめてみてください。CSP は「許可した出どころ以外のスクリプトは動かさない」仕組みなので、XSS で差し込まれたスクリプトも同じように止まります。

## つまずきポイント

> [!CAUTION]
> Web の問題は **「どこで」防ぐか** が問われる。クライアント側だけの対策や、文脈の違うエスケープは点にならない。

- <mark>**DOM ベース XSS はサーバ側で防げない**</mark>: フラグメントはサーバに届かない
- <mark>**認可はサーバ側で毎回**</mark>: ボタンを隠すのは対策ではない
- **ログイン成功時にセッション ID を作り直す**: 固定化攻撃の対策
- **SSRF は「サーバに内部へアクセスさせる」攻撃**: 接続先の許可リスト
- **CORS で Origin をそのまま返す誤り**: Cookie 付きと組み合わさると危険

## 重要な単語まとめ

| 用語 | 一言で言うと | 身近な実例 |
|---|---|---|
| **OWASP Top 10** | Web の重大リスクの上位 10 種 | 対策のチェックリスト |
| **反射型 / 格納型 / DOM ベース XSS** | URL から / 保存された投稿から / ブラウザの JS で | `#` 以降を書き込む JS |
| **文脈に応じたエスケープ** | 埋め込む場所ごとに違う無害化 | 属性値は引用符で囲む |
| **IDOR** | ID を変えると他人のデータが見える | `/orders/1002` |
| **セッション固定化** | 攻撃者の用意した ID でログインさせる | ログイン時に ID を再発行 |
| **SSRF** | サーバに内部へアクセスさせる | クラウドのメタデータの窃取 |
| **OS コマンドインジェクション** | 入力でコマンドを実行させる | `; rm -rf` |
| **パストラバーサル** | `../` で非公開ファイルを読む | 設定ファイルの漏えい |
| **CSP** | 実行してよいスクリプトの出どころを宣言 | XSS の被害の軽減 |
| **HSTS** | HTTPS でしか接続しないと覚えさせる | HTTP への格下げ防止 |
| **クリックジャッキング** | 透明な iframe の上で操作させる | `X-Frame-Options: DENY` |
