## 本文

### 1. 開発にセキュリティを組み込む

- **セキュリティ・バイ・デザイン**: 作り終わってから対策を足すのではなく、企画・設計の段階からセキュリティを考える
- **シフトレフト**: 工程表の左側（早い工程）でセキュリティの確認を行う。<mark>**設計の段階で見つけた問題は、リリース後に見つけるより、ずっと少ない手間で直せる**</mark>
- **DevSecOps**: 開発・セキュリティ・運用を一体にし、CI/CD（Web 編 Ch7）の中にセキュリティの検査を自動で組み込む

### 2. 脅威モデリング

設計の段階で、「誰が、どこから、何を狙って、どう攻めてくるか」を洗い出す作業です。

1. システムの構成とデータの流れを図にする（どこからどこへ、どんなデータが流れるか）
2. 信頼の境界（インターネットと社内、利用者とサーバ）を書き込む
3. 境界をまたぐところで起きうる脅威を挙げる。分類の型として **STRIDE**（なりすまし・改ざん・否認・情報漏えい・サービス妨害・権限昇格）がよく使われる
4. 脅威ごとに対策を決める

**実例**: Web 編 Ch5 の TODO アプリなら、「ブラウザ → API」の境界で、なりすまし（認証がない）、改ざん（HTTP のまま）、サービス妨害（大量の登録）などが挙がります。

### 3. セキュアコーディングと検査

- **入力は検証し、出力は文脈に合わせてエスケープする**（SC Chapter 4）
- **SQL はプレースホルダで組み立てる**（Web 編 Ch6）
- **秘密情報（API キー・パスワード）をコードに書かない**（Web 編 Ch7 の環境変数）
- **エラーメッセージに内部の情報を出さない**

| 検査 | 中身 | 見つけやすいもの |
|---|---|---|
| **SAST**（静的解析） | ソースコードを、動かさずに解析する | 危険な関数の使い方、SQL の文字列連結 |
| **DAST**（動的解析） | 動いているアプリに、外から攻撃に近い入力を送る | 実際に動く XSS・SQL インジェクション |
| **SCA**（構成の解析） | 使っているライブラリと、その既知の脆弱性を調べる | 古いライブラリ |
| **ファジング** | ランダムや異常な入力を大量に与えて、異常な動作を探す | 想定外の入力での停止 |
| **ペネトレーションテスト** | 専門家が攻撃者の立場で侵入を試みる | 複数の弱点の組合せ |

### 4. ソフトウェアのサプライチェーン

いまのソフトウェアは、大量のオープンソースのライブラリの上に作られています（Web 編 Ch5 の FastAPI も、それが依存する多くのライブラリの上に乗っています）。その **部品の供給の流れ** を狙う攻撃が増えています。

- **依存ライブラリの脆弱性**: 広く使われているライブラリに深刻な脆弱性が見つかると、それを使う無数のシステムが一斉に影響を受ける
- **悪意あるパッケージ**: 有名なパッケージと紛らわしい名前（タイポスクワッティング）の偽物を公開し、間違えて入れさせる
- **開発・配布の仕組みへの侵入**: 正規のソフトの更新の仕組みに侵入し、更新に見せかけてマルウェアを配る

> [!CAUTION]
> <mark>**「自分が書いたコードに脆弱性がない」ことは、システムに脆弱性がないことを意味しない**</mark>。依存しているライブラリ、その先のライブラリ、ビルドや配布の仕組みまでが攻撃の対象になる。使っている部品を一覧にして把握し、脆弱性情報と照らし合わせ続けることが対策の出発点。

**SBOM**（ソフトウェア部品表）は、ソフトウェアに含まれる部品（ライブラリの名前・バージョン・ライセンス）の一覧です。新しい脆弱性が公表されたときに、「うちのどの製品がそのライブラリを使っているか」をすぐに調べられます。

その他の対策:

- **バージョンを固定し、ハッシュ値で照合する**（Web 編 Ch7 の「依存ライブラリは固定する」）
- **依存関係の更新と脆弱性の監視を自動化する**（Dependabot、`pip-audit` など）
- **配布物に署名し、受け取る側で検証する**

### 5. クラウドのセキュリティ

#### 責任共有モデル

| 利用形態 | クラウド事業者が守る | 利用者が守る |
|---|---|---|
| IaaS | 設備・物理サーバ・仮想化基盤 | OS・ミドルウェア・アプリ・データ・アクセス権 |
| PaaS | 上に加えて OS・ミドルウェア | アプリ・データ・アクセス権 |
| SaaS | 上に加えてアプリ | データ・アクセス権・利用者の管理 |

どの形態でも、**データとアクセス権の管理は利用者の責任** です。

#### よくある事故

- **設定の誤り**: ストレージを誰でも読める設定で公開してしまう、管理画面をインターネットに開いてしまう。クラウドでの情報漏えいの原因で非常に多い。設定を継続的に点検する仕組み（**CSPM**）で見つける
- **権限の与えすぎ**: 何でもできる権限のアカウントやキーを、アプリや開発者に配ってしまう。**最小権限** にし、人には多要素認証を必須にする
- **アクセスキーの漏えい**: クラウドのキーを公開リポジトリに誤ってコミットし、数分で悪用される。キーはコードに書かず、秘密情報の管理サービスを使い、漏れたらすぐ無効化する
- **ログの未取得**: 誰がどんな操作をしたかの記録（監査ログ）を有効にしていないと、事故の調査ができない

### 6. 委託先・取引先の管理

- **委託先の選定**: セキュリティの体制を確かめてから選ぶ（認証の取得状況、チェックシートでの確認）
- **契約**: 守るべき事項、事故のときの報告の義務、再委託の条件、監査の権利を契約に入れる
- **継続的な確認**: 定期的な報告や監査で、実際に守られているかを確かめる
- **取引先経由の侵入**: 取引先のネットワークや、保守のためのリモート接続を経由して侵入される事例もある。接続の経路を把握し、必要なときだけ開ける

## 手を動かすパート

このリポジトリで使っている Python のライブラリについて、既知の脆弱性がないかを確かめてみます（SCA の体験）。

```powershell
pip install pip-audit
pip-audit -r requirements.txt
```

脆弱性が見つかれば、CVE の番号と、直っているバージョンが表示されます。また、`pip freeze` で表示される、実際に入っているライブラリとバージョンの一覧が、SBOM の素朴な形です。

## つまずきポイント

> [!CAUTION]
> 開発とクラウドの問題は **「誰の責任で、どの工程で」** 防ぐかを問う。正しい対策でも、担当や時期を誤ると答えにならない。

- <mark>**データとアクセス権は利用者の責任**</mark>: SaaS でも同じ
- <mark>**SAST と DAST の違い**</mark>: 動かさずにコードを見るか、動かして外から試すか
- <mark>**SBOM の目的**</mark>: 部品を把握して、脆弱性の影響をすぐ調べられるようにする
- **設定の誤りは最多の原因の 1 つ**: 公開範囲と権限を継続的に点検
- **キーは漏れる前提で**: コードに書かない、漏れたら無効化

## 重要な単語まとめ

| 用語 | 一言で言うと | 身近な実例 |
|---|---|---|
| **セキュリティ・バイ・デザイン / シフトレフト** | 設計から組み込む / 早い工程で確かめる | 設計レビューでの指摘 |
| **DevSecOps** | CI/CD にセキュリティ検査を組み込む | push のたびに自動検査 |
| **脅威モデリング / STRIDE** | 設計時に脅威を洗い出す / 脅威の 6 分類 | データの流れ図に境界を書く |
| **SAST / DAST / SCA** | 静的解析 / 動的解析 / ライブラリの脆弱性の検査 | `pip-audit` は SCA |
| **ファジング** | 異常な入力を大量に与える | 想定外の入力での停止の発見 |
| **ソフトウェアサプライチェーン攻撃** | 部品や配布の仕組みを狙う攻撃 | 偽のパッケージ |
| **SBOM** | ソフトウェアの部品表 | 脆弱性の影響調査 |
| **責任共有モデル** | クラウド事業者と利用者の分担 | データは利用者の責任 |
| **CSPM** | クラウドの設定の誤りを継続的に点検 | 公開ストレージの検出 |
| **最小権限** | 必要な権限だけを与える | 読み取り専用のキー |
