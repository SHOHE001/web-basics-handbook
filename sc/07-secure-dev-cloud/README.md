## 本文

### 1. 開発にセキュリティを組み込む

- **セキュリティ・バイ・デザイン**: 完成後に対策を付け足すのではなく、企画・設計の段階からセキュリティを考慮する
- **シフトレフト**: 工程表の左側（早い工程）でセキュリティを確認する。<mark>**設計段階で見つけた問題は、リリース後に見つけるよりもはるかに少ない手間で修正できる**</mark>
- **DevSecOps**: 開発・セキュリティ・運用を一体化し、CI/CD（Web 編 Ch7）のパイプラインにセキュリティ検査を自動で組み込む

### 2. 脅威モデリング

設計の段階で、「誰が、どこから、何を狙って、どのように攻撃してくるか」を洗い出す作業です。

1. システムの構成とデータの流れを図にする（どこからどこへ、どのようなデータが流れるか）
2. 信頼の境界（インターネットと社内、利用者とサーバなど）を書き込む
3. 境界をまたぐ箇所で起こり得る脅威を挙げる。分類の枠組みとして **STRIDE**（なりすまし・改ざん・否認・情報漏えい・サービス妨害・権限昇格）がよく使われる
4. 脅威ごとに対策を決める

**実例**: Web 編 Ch5 の TODO アプリであれば、「ブラウザ → API」の境界において、なりすまし（認証がない）、改ざん（HTTP のまま通信している）、サービス妨害（大量の登録リクエスト）などが挙げられます。

### 3. セキュアコーディングと検査

- **入力値は検証し、出力値は文脈に合わせてエスケープする**（SC Chapter 4）
- **SQL はプレースホルダを使って組み立てる**（Web 編 Ch6）
- **秘密情報（API キー・パスワード）をコードに埋め込まない**（Web 編 Ch7 の環境変数）
- **エラーメッセージに内部情報を表示しない**

| 検査 | 中身 | 見つけやすいもの |
|---|---|---|
| **SAST**（静的解析） | ソースコードを動かさずに解析する | 危険な関数の使用、SQL の文字列連結 |
| **DAST**（動的解析） | 稼働中のアプリに外部から攻撃に近い入力を送る | 実際に発動する XSS・SQL インジェクション |
| **SCA**（構成の解析） | 使用しているライブラリと、その既知の脆弱性を調べる | 古いライブラリ |
| **ファジング** | ランダムな値や異常な入力を大量に与えて、不正な動作を探す | 想定外の入力による停止 |
| **ペネトレーションテスト** | 専門家が攻撃者の視点で侵入を試みる | 複数の弱点の組み合わせ |

### 4. ソフトウェアのサプライチェーン

現在のソフトウェアは、大量のオープンソースライブラリの上に成り立っています（Web 編 Ch5 の FastAPI も、それが依存する多くのライブラリの上で動いています）。このような **部品の供給経路（サプライチェーン）** を狙う攻撃が増えています。

- **依存ライブラリの脆弱性**: 広く使われているライブラリに深刻な脆弱性が見つかると、それを利用する無数のシステムが一斉に影響を受ける
- **悪意あるパッケージ**: 有名なパッケージと紛らわしい名前（タイポスクワッティング）の偽物を公開し、誤って導入させる
- **開発・配布の仕組みへの侵入**: 正規ソフトウェアの更新システムに侵入し、アップデートを装ってマルウェアを配布する

> [!CAUTION]
> <mark>**「自分が書いたコードに脆弱性がない」からといって、システム全体に脆弱性がないとは限らない**</mark>。直接利用しているライブラリやその先の依存ライブラリ、さらにはビルドや配布の仕組みまでが攻撃対象になる。使用している部品を一覧化して把握し、脆弱性情報と照らし合わせ続けることが対策の出発点である。

**SBOM**（ソフトウェア部品表）は、ソフトウェアに含まれる部品（ライブラリの名前・バージョン・ライセンス）の一覧です。新たな脆弱性が公表された際、「自社のどの製品がそのライブラリを使っているか」をすぐに調査できます。

その他の対策:

- **バージョンを固定し、ハッシュ値で照合する**（Web 編 Ch7 の「依存ライブラリは固定する」）
- **依存関係の更新と脆弱性の監視を自動化する**（Dependabot、`pip-audit` など）
- **配布物に署名し、受け取る側で検証する**

### 5. クラウドのセキュリティ

#### 責任共有モデル

| 利用形態 | クラウド事業者が守る | 利用者が守る |
|---|---|---|
| IaaS | 設備・物理サーバ・仮想化基盤 | OS・ミドルウェア・アプリ・データ・アクセス権 |
| PaaS | 上記に加えて OS・ミドルウェア | アプリ・データ・アクセス権 |
| SaaS | 上記に加えてアプリ | データ・アクセス権・利用者の管理 |

どの利用形態であっても、**データとアクセス権の管理は利用者の責任** です。

#### よくある事故

- **設定の誤り**: ストレージを誰でも閲覧できる設定で公開してしまう、管理画面をインターネットに開放してしまうといったミス。クラウドにおける情報漏えいの原因として非常に多い。設定を継続的に点検する仕組み（**CSPM**）で検出する
- **権限の与えすぎ**: 何でも実行できる強い権限のアカウントやキーを、アプリや開発者に付与してしまう。**最小権限** を徹底し、人間のアカウントには多要素認証を必須とする
- **アクセスキーの漏えい**: クラウドのアクセスキーを公開リポジトリに誤ってコミットすると、わずか数分で悪用される。キーはコード内に記述せず秘密情報の管理サービスを利用し、漏えいした場合は直ちに無効化する
- **ログの未取得**: 誰がどのような操作をしたかの記録（監査ログ）を有効にしていないと、事故発生時の原因調査ができない

### 6. 委託先・取引先の管理

- **委託先の選定**: セキュリティ体制を確認してから選定する（認証の取得状況やチェックシートによる確認）
- **契約**: 遵守事項、事故発生時の報告義務、再委託の条件、監査の権利を契約に盛り込む
- **継続的な確認**: 定期的な報告や監査を通じて、ルールが実際に守られているかを確認する
- **取引先経由の侵入**: 取引先のネットワークや、保守用のリモート接続を経由して侵入される事例もある。接続経路を把握し、必要なときだけ開放する

## 手を動かすパート

このリポジトリで使用している Python ライブラリに、既知の脆弱性がないかを確認してみます（SCA の体験）。

```powershell
pip install pip-audit
pip-audit -r requirements.txt
```

脆弱性が見つかれば、CVE 番号と修正済みバージョンが表示されます。また、`pip freeze` で表示される「実際にインストールされているライブラリとバージョンの一覧」が、SBOM の素朴な形にあたります。

## つまずきポイント

> [!CAUTION]
> 開発とクラウドに関する問題では、**「誰の責任で、どの工程で」** 防ぐかが問われる。対策の内容が正しくても、担当者や時期を誤ると正解にはならない。

- <mark>**データとアクセス権は利用者の責任**</mark>: SaaS であっても変わらない
- <mark>**SAST と DAST の違い**</mark>: 動かさずにコードを見るか、動かして外部から試すか
- <mark>**SBOM の目的**</mark>: 構成部品を把握し、脆弱性の影響を即座に調査できるようにする
- **設定の誤りは最多の原因の 1 つ**: 公開範囲と権限を継続的に点検する
- **キーは漏れる前提で扱う**: コードに書かない、漏れたら即座に無効化する

| 用語 | 一言で言うと | 身近な実例 |
|---|---|---|
| **セキュリティ・バイ・デザイン / シフトレフト** | 設計段階から組み込む / 早い工程で確認する | 設計レビューでの指摘 |
| **DevSecOps** | CI/CD にセキュリティ検査を組み込む | push のたびに自動検査 |

| **SAST / DAST / SCA** | 静的解析 / 動的解析 / ライブラリの脆弱性検査 | `pip-audit` は SCA |
| **ファジング** | 異常な入力を大量に与える | 想定外の入力による停止の発見 |
| **ソフトウェアサプライチェーン攻撃** | 部品や配布の仕組みを狙う攻撃 | 偽パッケージの公開 |
| **SBOM** | ソフトウェアの部品表 | 脆弱性の影響調査 |
| **責任共有モデル** | クラウド事業者と利用者の責任分担 | データは利用者の責任 |
| **CSPM** | クラウドの設定ミスを継続的に点検 | 公開ストレージの検出 |
| **最小権限** | 必要な権限のみを付与する | 読み取り専用のキー |
