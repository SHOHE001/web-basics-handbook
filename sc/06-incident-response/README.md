## 本文

### 1. 対応の段階

インシデント対応は、米国 NIST のガイドラインなどで、おおむね次の段階に整理されています。

1. **準備**: 体制（CSIRT）、連絡先、手順書、ログの取得、訓練を、起きる前に整えておく
2. **検知・分析**: 異常に気付き、本当にインシデントか、影響の範囲と深刻度はどれくらいかを見極める
3. **封じ込め**: 被害の拡大を止める（感染端末の隔離、不正に使われたアカウントの停止、攻撃元との通信の遮断）
4. **根絶**: 原因を取り除く（マルウェアの除去、脆弱性の修正、攻撃者が仕掛けた裏口の削除）
5. **復旧**: 安全を確かめてから、システムを元に戻し、しばらく監視を強める
6. **事後の活動**: 振り返り、再発防止策、報告

> [!CAUTION]
> <mark>**封じ込めの前に根絶や復旧に手を付けない**</mark>。攻撃者がまだ中にいる状態でバックアップから戻しても、同じ経路でまた入られる。また、侵入の範囲を調べ終わる前に 1 台だけ急いで隔離すると、攻撃者に気付かれて痕跡を消されたり、ほかの端末で活動を早められたりすることもある。科目 B では「この時点で行うべき対応」を、段階の順番で判断させる設問が多い。

### 2. 優先度と連絡

#### 優先度（トリアージ）

複数のインシデントが同時に起きたとき、または 1 つのインシデントの中でも、何から対応するかを決めます。判断の材料は、影響を受ける業務の重要性、データの機密性、被害が広がる速さ、法令の報告義務の有無などです。

#### 連絡と報告

| 相手 | 中身 |
|---|---|
| **経営層** | 事実・影響・判断が必要な事項（サービスを止めるか、公表するか） |
| **社内の関係部署** | 法務・広報・顧客窓口と、公表や問合せの対応を準備する |
| **顧客・取引先** | 影響がある場合に、分かっている事実と対応を伝える |
| **個人情報保護委員会** | 個人情報の漏えいなどで報告義務がある場合（速報・確報） |
| **警察** | 犯罪被害として相談・届出する |
| **JPCERT/CC・IPA** | インシデントの報告・相談。ほかの組織への注意喚起にもつながる |

公表するときは、事実と推測を分け、分かっていないことは「調査中」と書きます。

### 3. CSIRT と連携

- **CSIRT**: 組織の中で、インシデントの受付・判断・対応・調整を行うチーム。専任でなくても、役割を決めておくことが大切
- **PoC**（窓口）: 外部からの「御社のサーバから攻撃が来ている」といった連絡を受ける窓口を公開しておく。窓口がないと、外部からの重要な通知を受け取れない
- **連携する組織**: JPCERT/CC（国内の調整役）、業界ごとの情報共有の枠組み（ISAC）、日本シーサート協議会など

### 4. デジタルフォレンジック

インシデントの原因や経緯を明らかにし、必要なら法的な証拠として使えるように、電子的な証拠を集めて分析することです。

#### 証拠保全の順番

<mark>**消えやすいものから先に保全する**</mark>（揮発性の順序）のが原則です。

1. CPU のレジスタ・キャッシュ
2. メモリの内容、実行中のプロセス、ネットワークの接続状態
3. 一時ファイル
4. ディスクの内容
5. 外部に保存されたログ、バックアップ

電源を切るとメモリの内容は消えるので、AP Chapter 4 で見た「電源を切らずにネットワークから切り離す」は、この順番を守るための手順でもあります。

#### 証拠の扱い

- **複製を作って、複製の方を調べる**: 元の媒体を直接調べると、調べる操作で中身が変わってしまう。ディスクを丸ごと 1 ビットずつ写した複製（イメージ）を作る
- **ハッシュ値で同一性を示す**: 元の媒体と複製のハッシュ値（SHA-256 など）を記録し、同じであることを示す。分析の途中でも、複製が変わっていないことを確かめられる
- **証拠の管理の連続性**（Chain of Custody）: 誰が、いつ、どこで証拠を受け取り、保管し、何をしたかを、途切れなく記録する。記録が途切れると、法的な証拠としての信頼性が下がる

### 5. 事後の振り返り

- **事実の時系列**: いつ侵入され、いつ気付き、いつ何をしたか
- **うまくいったこと・いかなかったこと**: 検知までにかかった時間、連絡の遅れ、手順書の不備
- **根本原因と再発防止策**: 技術的な対策（修正、設定の変更）と、運用・体制の対策（監視の強化、教育、手順書の改訂）
- **責任の追及ではなく改善のため**: 失敗を報告しにくい雰囲気になると、次のインシデントの発見が遅れる

### 6. 事業継続（BCP）との関係

大規模なインシデント（ランサムウェアで基幹システムが止まる、など）は、災害と同じように事業の継続を脅かします。

- **BCP**（事業継続計画）: 重要な業務を、決めた時間内に、決めた水準で再開するための計画
- **BIA**（事業影響度分析）: どの業務が止まると、どれくらいの時間でどんな影響が出るかを分析し、優先順位と目標（RTO・RPO、AP Chapter 2）を決める
- **紙やほかの手段での代替**: システムが止まっている間、業務をどう回すか（電子カルテが止まった病院が紙で診療を続ける、など）

## 手を動かすパート

ハッシュ値で「複製が元と同じ」ことを示す流れを、Python で試せます。

```python
import hashlib, shutil, pathlib

src = pathlib.Path("evidence.log")
src.write_text("2026-11-04 09:02 login alice\n2026-11-04 23:41 login bob\n", encoding="utf-8")
shutil.copy2(src, "evidence_copy.log")

def sha256(path):
    return hashlib.sha256(pathlib.Path(path).read_bytes()).hexdigest()

print("元  :", sha256("evidence.log"))
print("複製:", sha256("evidence_copy.log"))
print("同一:", sha256("evidence.log") == sha256("evidence_copy.log"))
```

複製のファイルを 1 文字でも書き換えてから、もう一度ハッシュ値を比べてみてください。

## つまずきポイント

> [!CAUTION]
> インシデント対応の問題は **「今、この時点で何をするか」** の順番を問う。正しい対応でも、時期を誤ると不正解になる。

- <mark>**封じ込め → 根絶 → 復旧の順番**</mark>: 攻撃者がいるうちに戻さない
- <mark>**揮発性の高いものから保全**</mark>: メモリ → ディスク → 外部のログ
- <mark>**調べるのは複製**</mark>: 元の媒体はハッシュ値を記録して保管
- **証拠の管理の連続性**: 誰がいつ何をしたかを途切れなく記録
- **公表は事実と推測を分ける**: 分からないことは「調査中」

## 重要な単語まとめ

| 用語 | 一言で言うと | 身近な実例 |
|---|---|---|
| **封じ込め / 根絶 / 復旧** | 拡大を止める / 原因を除く / 元に戻す | 隔離 → 駆除 → 再開 |
| **トリアージ** | 対応の優先度を決める | 重要業務への影響から |
| **CSIRT / PoC** | 対応チーム / 外部からの連絡窓口 | security@ のような窓口 |
| **JPCERT/CC / ISAC** | 国内の調整役 / 業界の情報共有の枠組み | 注意喚起の発信 |
| **デジタルフォレンジック** | 電子的な証拠の収集と分析 | 侵入経路の調査 |
| **揮発性の順序** | 消えやすいものから保全 | メモリが先 |
| **ディスクイメージ** | 媒体を丸ごと写した複製 | 調べるのは複製 |
| **証拠の管理の連続性** | 証拠の扱いの途切れない記録 | 法的な証拠能力 |
| **BCP / BIA** | 事業継続計画 / 事業影響度分析 | 紙での代替運用 |
