## 本文

### 1. 暗号の安全性

- **危殆化**（きたいか）: 計算機の性能向上や解読法の発見で、暗号が安全でなくなること。かつて使われた DES、SHA-1、RSA 1024 ビットなどは、新しく使うべきではないとされている
- **暗号の移行**: 危殆化に備えて、使っている暗号を切り替えられるように設計しておくこと（クリプトアジリティ）
- **耐量子計算機暗号**（PQC）: 将来の量子コンピュータでも解読が難しいとされる暗号。米国 NIST が 2024 年に最初の標準を公表し、移行の準備が始まっている
- **前方秘匿性**（Forward Secrecy）: サーバの秘密鍵が後で漏れても、過去の通信が解読されない性質。通信のたびに使い捨ての鍵を交換する（一時的な Diffie-Hellman 鍵交換、ECDHE）ことで実現する。TLS 1.3 では必ずこの方式になる

### 2. 共通鍵暗号の利用モード

AES のようなブロック暗号は、決まった長さ（128 ビット）ずつ暗号化します。長いデータをどうつなげて暗号化するかが **利用モード** です。

| モード | 特徴 |
|---|---|
| **ECB** | ブロックごとに独立して暗号化。同じ平文のブロックは同じ暗号文になり、模様が透けて見える。使うべきではない |
| **CBC** | 前のブロックの暗号文を次のブロックに混ぜる。最初のブロック用に初期化ベクトル（IV）が必要 |
| **CTR** | カウンタを暗号化した値と平文を XOR する。並列に処理できる |
| **GCM** | CTR に改ざん検知の仕組みを組み合わせた **認証付き暗号**（AEAD）。暗号化と完全性の確認を同時に行う |

> [!CAUTION]
> <mark>**暗号化だけでは改ざんを防げない**</mark>。CBC や CTR で暗号化したデータは、中身が読めなくても、ビットを書き換えられると復号結果も変わってしまう。暗号化と一緒に MAC を付けるか、GCM のような認証付き暗号を使う。TLS 1.3 は認証付き暗号しか使わない。

### 3. MAC とパスワードの保存

#### MAC と HMAC

**MAC**（メッセージ認証コード）は、共通鍵を使ってメッセージから作る短い値で、受け取った側が同じ鍵で計算し直して一致すれば、「鍵を知っている相手から届き、改ざんされていない」と分かります。ハッシュ関数を使った MAC が **HMAC** です。

デジタル署名（公開鍵暗号）との違いは、MAC は送信者と受信者が同じ鍵を持つので、**第三者に対して「どちらが作ったか」を証明できない**（否認防止にならない）ことです。

#### パスワードの保存

| 方式 | 評価 |
|---|---|
| 平文のまま | 論外 |
| 汎用のハッシュ（SHA-256）だけ | 同じパスワードは同じハッシュ値になり、事前に計算した表（レインボーテーブル）で調べられる |
| ソルト付きハッシュ | 利用者ごとのランダムな値（ソルト）を混ぜて、表での一括解読を防ぐ。ただし計算が速いので総当たりには弱い |
| **ストレッチング付き**（bcrypt・scrypt・Argon2・PBKDF2） | 意図的に計算を重くして、総当たりの速度を落とす。現在の推奨 |

さらに、ソルトとは別にサーバ側だけで管理する秘密の値（**ペッパー**）を混ぜることもあります。

### 4. TLS 1.3

#### ハンドシェイクの流れ

1. **ClientHello**: クライアントが、使える暗号の一覧と、鍵交換の材料（鍵共有の値）を送る
2. **ServerHello**: サーバが暗号を選び、自分の鍵共有の値を返す。この時点で両者は共通の鍵を作れる
3. 以降は暗号化された状態で、サーバの **証明書** と、その証明書の秘密鍵を持っていることを示す署名（CertificateVerify）を送る
4. クライアントが証明書を検証し、完了の通知（Finished）を交わして、アプリケーションのデータを送る

ここまでが 1 往復です（Web 編 Ch3 の NOTE）。前回つないだことがあれば、最初のメッセージと一緒にデータを送る **0-RTT** も使えますが、0-RTT のデータは攻撃者に再送（リプレイ）されるおそれがあるので、何度送られても困らない要求に限ります。

#### 証明書の検証

クライアントは次を確かめます。

- 証明書の発行者をたどって、信頼している **ルート認証局** までつながるか（証明書チェーン）
- 有効期限内か
- 証明書に書かれたドメイン名が、接続先と一致するか
- **失効** していないか。失効の確認には、失効した証明書の一覧（**CRL**）、その場で問い合わせる **OCSP**、サーバが OCSP の応答を一緒に渡す **OCSP ステープリング** がある。最近は、証明書の有効期間そのものを短くして、失効の確認に頼る度合いを減らす流れもある（Let's Encrypt の有効期間の短縮など）

**証明書の透明性**（CT）: 認証局が発行した証明書を公開のログに記録する仕組み。自分のドメインに対して、身に覚えのない証明書が発行されていないかを監視できます。

### 5. 認証方式の深掘り

#### チャレンジレスポンス

サーバがランダムな値（チャレンジ）を送り、クライアントは秘密の情報を使ってそれを加工した値（レスポンス）を返します。パスワードそのものはネットワークに流れず、チャレンジが毎回違うので、盗聴した値を再送しても通りません。

#### Kerberos

社内ネットワーク（Windows の Active Directory など）で使われるシングルサインオンの仕組みです。

1. 利用者は最初に認証サーバに認証してもらい、**チケット**（TGT）を受け取る
2. サービスを使うときは、TGT を見せてそのサービス用のチケットをもらう
3. サービスにはそのチケットを見せる。パスワードを何度も入力しない

チケットに有効期限があるため、<mark>**関係するサーバの時刻がずれていると認証に失敗する**</mark>（時刻同期が前提）。

#### パスキー（FIDO2 / WebAuthn）

1. 登録時に、端末が **そのサイト専用** の鍵ペアを作り、公開鍵だけをサイトに登録する
2. ログイン時、サイトがチャレンジを送り、端末は秘密鍵で署名して返す。秘密鍵を使うには端末の生体認証や PIN が必要
3. 端末は、署名を求めてきたサイトのドメインを確かめるので、**偽サイトには署名しない**

サーバに漏れて困る秘密（パスワード）がそもそも保存されない、という点が強みです。

#### OAuth 2.0 の流れと PKCE

代表的な **認可コードフロー** は次のとおりです。

1. 利用者がアプリ（クライアント）から、認可サーバ（Google など）のログイン画面に移る
2. 利用者がログインして、アプリへの許可に同意する
3. 認可サーバが、アプリに短命の **認可コード** を渡す（ブラウザのリダイレクトで）
4. アプリが認可コードを認可サーバに送り、**アクセストークン** と交換する
5. アプリはアクセストークンを使って API を呼ぶ

スマホアプリやブラウザだけで動くアプリは、秘密の値を安全に持てないので、認可コードを横取りされると悪用されます。これを防ぐのが **PKCE** です。アプリが最初にランダムな値を作ってそのハッシュを送り、トークンと交換するときに元の値を見せることで、コードを横取りした別のアプリには交換できなくします。

## つまずきポイント

> [!CAUTION]
> 暗号と認証は **「何を守れて、何を守れないか」** を正確に言えるかが問われる。仕組みの名前だけ覚えていると、記述で答えられない。

- <mark>**暗号化と改ざん検知は別**</mark>: 認証付き暗号か MAC を組み合わせる
- <mark>**MAC は否認防止にならない**</mark>: 送信者と受信者が同じ鍵を持つから
- <mark>**ソルトとストレッチングの役割の違い**</mark>: 表での一括解読を防ぐ / 総当たりを遅くする
- **0-RTT はリプレイに注意**: 何度送られても困らない要求に限る
- **Kerberos は時刻同期が前提**: ずれるとチケットの検証に失敗する

## 重要な単語まとめ

| 用語 | 一言で言うと | 身近な実例 |
|---|---|---|
| **危殆化** | 暗号が安全でなくなること | SHA-1 は新規利用しない |
| **耐量子計算機暗号（PQC）** | 量子計算機でも解読が難しい暗号 | 移行の準備が進行中 |
| **前方秘匿性** | 秘密鍵が漏れても過去の通信は守られる | TLS 1.3 の ECDHE |
| **ECB / CBC / CTR / GCM** | 暗号の利用モード | GCM は認証付き暗号 |
| **MAC / HMAC** | 共通鍵による改ざん検知の値 / ハッシュを使った MAC | API の署名付きリクエスト |
| **ソルト / ストレッチング** | 利用者ごとのランダム値 / 計算を重くする工夫 | bcrypt、Argon2 |
| **CRL / OCSP / ステープリング** | 失効の一覧 / その場の問い合わせ / サーバが応答を添付 | 証明書の失効確認 |
| **証明書の透明性（CT）** | 発行された証明書を公開ログに記録 | 不正発行の監視 |
| **チャレンジレスポンス** | 毎回違う値を秘密で加工して返す | パスワードを流さない認証 |
| **Kerberos / チケット** | 社内向けシングルサインオン / 認証済みの証 | Active Directory |
| **パスキー（FIDO2）** | サイト専用の鍵ペアで署名するログイン | 指紋でログイン |
| **認可コードフロー / PKCE** | OAuth の代表的な流れ / コード横取り対策 | スマホアプリの Google 連携 |
