## 本文

### 1. 暗号の安全性

- **危殆化**（きたいか）: 計算機の性能向上や解読法の発見により、暗号が安全でなくなることです。かつて使われていた DES、SHA-1、RSA 1024 ビットなどは、新しく使うべきではないとされています
- **暗号の移行**: 危殆化に備えて、使用している暗号を切り替えられるように設計しておくことです（クリプトアジリティ）
- **耐量子計算機暗号**（PQC）: 将来の量子コンピュータでも解読が難しいとされる暗号です。米国 NIST が 2024 年に最初の標準を公表し、移行の準備が始まっています
- **前方秘匿性**（Forward Secrecy）: サーバの秘密鍵が後から漏洩しても、過去の通信が解読されない性質です。通信のたびに使い捨ての鍵を交換する方式（一時的な Diffie-Hellman 鍵交換、ECDHE）によって実現します。TLS 1.3 では必ずこの方式が使われます

### 2. 共通鍵暗号の利用モード

AES のようなブロック暗号は、決まった長さ（128 ビット）ごとにデータを暗号化します。長いデータをどのようにつなげて暗号化するかという方式が **利用モード** です。

| モード | 特徴 |
|---|---|
| **ECB** | ブロックごとに独立して暗号化する。同じ平文のブロックは同じ暗号文になるため、元の模様が透けて見えてしまう。使うべきではない |
| **CBC** | 前のブロックの暗号文を次のブロックに混ぜて暗号化する。最初のブロック用に初期化ベクトル（IV）が必要になる |
| **CTR** | カウンタを暗号化した値と平文を XOR する。並列に処理できる |
| **GCM** | CTR に改ざん検知の仕組みを組み合わせた **認証付き暗号**（AEAD）。暗号化と完全性の確認を同時に行う |

> [!CAUTION]
> <mark>**暗号化だけでは改ざんを防げません**</mark>。CBC や CTR で暗号化したデータは、中身を読めなくても、ビットを書き換えられると復号結果まで変わってしまいます。暗号化とあわせて MAC を付与するか、GCM のような認証付き暗号を使う必要があります。TLS 1.3 では認証付き暗号しか使われません。

### 3. MAC とパスワードの保存

#### MAC と HMAC

**MAC**（メッセージ認証コード）は、共通鍵を使ってメッセージから生成する短い値です。受信側が同じ鍵で計算し直して値が一致すれば、「鍵を知っている相手から届いたこと」と「改ざんされていないこと」が分かります。ハッシュ関数を使った MAC が **HMAC** です。

デジタル署名（公開鍵暗号）との違いは、MAC では送信者と受信者が同じ鍵を共有するため、**第三者に対して「どちらが作成したか」を証明できない**（否認防止にならない）点にあります。

#### パスワードの保存

| 方式 | 評価 |
|---|---|
| 平文のまま | 論外 |
| 汎用のハッシュ（SHA-256）のみ | 同じパスワードは同じハッシュ値になるため、事前計算した表（レインボーテーブル）で割り出される |
| ソルト付きハッシュ | 利用者ごとに異なるランダムな値（ソルト）を混ぜることで、表を使った一括解読を防ぐ。ただし計算が速いため総当たり攻撃には弱い |
| **ストレッチング付き**（bcrypt・scrypt・Argon2・PBKDF2） | 意図的に計算処理を重くして、総当たり攻撃の速度を落とす。現在の推奨方式 |

さらに、ソルトとは別に、サーバ側だけで管理する秘密の値（**ペッパー**）を混ぜることもあります。

### 4. TLS 1.3

#### ハンドシェイクの流れ

1. **ClientHello**: クライアントが、使用できる暗号の一覧と、鍵交換の材料（鍵共有の値）を送ります
2. **ServerHello**: サーバが暗号を選び、自身の鍵共有の値を返します。この時点で、双方が共通の鍵を生成できます
3. 以降は暗号化された状態で、サーバの **証明書** と、その証明書の秘密鍵を保持していることを示す署名（CertificateVerify）を送ります
4. クライアントが証明書を検証し、完了通知（Finished）を交わしてから、アプリケーションのデータを送ります

ここまでが 1 往復です（Web 編 Ch3 の NOTE）。過去に接続したことがあれば、最初のメッセージと一緒にデータを送る **0-RTT** も使えます。ただし、0-RTT のデータは攻撃者に再送（リプレイ）されるおそれがあるため、何度送られても問題ない要求に限って使います。

#### 証明書の検証

クライアントは次の点を確認します。

- 証明書の発行者をたどって、信頼している **ルート認証局** までつながるか（証明書チェーン）
- 有効期限内か
- 証明書に記載されたドメイン名が、接続先と一致するか
- **失効** していないか。失効の確認方法には、失効した証明書の一覧（**CRL**）、その場で問い合わせる **OCSP**、サーバが OCSP の応答をあわせて渡す **OCSP ステープリング** があります。最近では、証明書の有効期間そのものを短くして、失効確認に頼る割合を減らす動きもあります（Let's Encrypt における有効期間の短縮など）

**証明書の透明性**（CT）: 認証局が発行した証明書を公開ログに記録する仕組みです。自分のドメインに対して、身に覚えのない証明書が発行されていないかを監視できます。

### 5. 認証方式の深掘り

#### チャレンジレスポンス

サーバがランダムな値（チャレンジ）を送り、クライアントは秘密の情報を使ってそれを加工した値（レスポンス）を返します。パスワードそのものはネットワーク上を流れず、チャレンジの値も毎回変わるため、盗聴した値を再送しても認証は通りません。

#### Kerberos

社内ネットワーク（Windows の Active Directory など）で使われるシングルサインオンの仕組みです。

1. 利用者は最初に認証サーバで認証を受け、**チケット**（TGT）を受け取ります
2. サービスを利用する際は、TGT を提示してそのサービス用のチケットを受け取ります
3. サービスにはそのチケットを提示します。パスワードを何度も入力する必要はありません

チケットには有効期限があるため、<mark>**関係するサーバ間で時刻がずれていると認証に失敗します**</mark>（時刻同期が前提となります）。

#### パスキー（FIDO2 / WebAuthn）

1. 登録時に、端末が **そのサイト専用** の鍵ペアを生成し、公開鍵だけをサイトに登録します
2. ログイン時、サイトがチャレンジを送り、端末は秘密鍵で署名して返します。秘密鍵を使うには、端末での生体認証や PIN の入力が必要です
3. 端末は署名を要求してきたサイトのドメインを確認するため、**偽サイトに対しては署名しません**

サーバ側に漏洩して困る秘密情報（パスワード）がそもそも保存されない点が強みです。

#### OAuth 2.0 の流れと PKCE

代表的な **認可コードフロー** の手順は次のとおりです。

1. 利用者がアプリ（クライアント）から、認可サーバ（Google など）のログイン画面へ移動します
2. 利用者がログインし、アプリへの権限付与に同意します
3. 認可サーバが、ブラウザのリダイレクトを通じてアプリに短命な **認可コード** を渡します
4. アプリが認可コードを認可サーバに送り、**アクセストークン** と交換します
5. アプリはアクセストークンを使って API を呼び出します

スマホアプリやブラウザだけで動作するアプリは、秘密の値を安全に保持できないため、認可コードを横取りされると悪用されてしまいます。これを防ぐ仕組みが **PKCE** です。アプリが最初にランダムな値を生成してそのハッシュ値を送り、トークンと交換する際に元の値を提示することで、コードを横取りした別のアプリでは交換できないようにします。

## つまずきポイント

> [!CAUTION]
> 暗号と認証では、**「何を守れて、何を守れないか」** を正確に説明できるかが問われます。仕組みの名前だけを覚えていると、記述問題で答えられません。

- <mark>**暗号化と改ざん検知は別物**</mark>: 認証付き暗号を使うか、MAC を組み合わせる
- <mark>**MAC は否認防止にならない**</mark>: 送信者と受信者が同じ鍵を共有するため
- <mark>**ソルトとストレッチングの役割の違い**</mark>: 表を使った一括解読を防ぐ / 総当たり攻撃を遅くする
- **0-RTT はリプレイ攻撃に注意**: 何度送られても問題ない要求に限る
- **Kerberos は時刻同期が前提**: 時刻がずれるとチケットの検証に失敗する

## 重要な単語まとめ

| 用語 | 一言で言うと | 身近な実例 |
|---|---|---|
| **危殆化** | 暗号が安全でなくなること | SHA-1 は新規利用しない |
| **耐量子計算機暗号（PQC）** | 量子計算機でも解読が難しい暗号 | 移行の準備が進行中 |
| **前方秘匿性** | 秘密鍵が漏れても過去の通信は守られる性質 | TLS 1.3 の ECDHE |
| **ECB / CBC / CTR / GCM** | 暗号の利用モード | GCM は認証付き暗号 |
| **MAC / HMAC** | 共通鍵による改ざん検知の値 / ハッシュを使った MAC | API の署名付きリクエスト |
| **ソルト / ストレッチング** | 利用者ごとのランダム値 / 計算を重くする工夫 | bcrypt、Argon2 |
| **CRL / OCSP / ステープリング** | 失効の一覧 / その場の問い合わせ / サーバが応答を添付 | 証明書の失効確認 |
| **証明書の透明性（CT）** | 発行された証明書を公開ログに記録する仕組み | 不正発行の監視 |
| **チャレンジレスポンス** | 毎回違う値を秘密情報で加工して返す方式 | パスワードを流さない認証 |
| **Kerberos / チケット** | 社内向けシングルサインオン / 認証済みの証 | Active Directory |
| **パスキー（FIDO2）** | サイト専用の鍵ペアで署名するログイン方式 | 指紋でログイン |
| **認可コードフロー / PKCE** | OAuth の代表的な流れ / コード横取り対策 | スマホアプリの Google 連携 |
