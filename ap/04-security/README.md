## 本文

### 1. 問 1 の出題傾向

問 1 は、ある組織で起きたセキュリティの出来事（不審なメール、マルウェア感染、不正ログイン、情報漏えいなど）と、その組織のネットワーク構成や運用ルールが示され、次のようなことを問われます。

- 攻撃の手口や、被害が広がった **原因**
- 原因に対する **技術的な対策** と **運用上の対策**
- ログや通信記録から **何が分かるか**
- ファイアウォールのルールや設定の **誤りの指摘**

知識の比重は FE より大きいものの、答えの根拠が本文にあるのは他の分野と同じです（AP Chapter 3）。

### 2. メールのなりすまし対策

送信元を偽ったメールを見分けるための仕組みです。最近の出題の定番で、Gmail などの大手が大量送信者にこれらの設定を求めるようになってからは、実務でも必須になっています。

| 仕組み | 何で確かめるか | 分かること |
|---|---|---|
| **SPF** | 送信元ドメインの DNS に「このドメインのメールを送ってよいサーバの IP アドレス」を登録しておき、受信側が照合する | 送ってきたサーバが正規のものか |
| **DKIM** | 送信側がメールに電子署名を付け、受信側が DNS に登録された公開鍵で検証する | 途中で改ざんされていないか、署名したドメイン |
| **DMARC** | SPF・DKIM の結果と、見た目の差出人（From）のドメインが一致するかを確かめ、失敗したメールの扱い（受け取る・隔離・拒否）を送信側が DNS で宣言する | なりすましメールをどう処理するか |

> [!CAUTION]
> <mark>**SPF と DKIM だけでは、画面に表示される差出人（From）の偽装は防げない**</mark>。SPF が確かめるのは配送上の送信元で、利用者が見る From 欄とは別物だからである。From 欄と照合して扱いを決めるのが DMARC。「SPF を設定したのに偽メールが届いた理由」はこの組合せで答える。

### 3. 認証の強化

| 仕組み | 役割 |
|---|---|
| **多要素認証** | 知識・所有・生体のうち 2 つ以上を組み合わせる（FE Chapter 8） |
| **パスキー**（FIDO2 / WebAuthn） | 端末内の秘密鍵で署名してログインする。秘密鍵は端末から出ず、登録したサイト以外では使えないので、フィッシングに強い |
| **OAuth 2.0** | 利用者のパスワードを渡さずに、あるサービスが別のサービスの機能を **使ってよいという許可（認可）** を受け取る仕組み |
| **OpenID Connect** | OAuth 2.0 の上に、**利用者が誰か（認証）** を伝える仕組みを足したもの。「Google でログイン」の中身 |
| **SAML** | 組織のシステムどうしでシングルサインオンを実現する仕組み。企業向けのクラウドサービスでよく使う |

**実例**: カレンダーアプリが「Google カレンダーへのアクセスを許可しますか？」と聞いてくるのが OAuth（何をしてよいかの許可）、「Google でログイン」ボタンが OpenID Connect（誰かの確認）です。

### 4. ネットワークの区画と通信制御

#### 区画の分け方

```
インターネット
     │
 [ファイアウォール]
     ├── DMZ（公開 Web サーバ、メール中継サーバ、DNS サーバ）
     └── 社内 LAN（業務 PC、ファイルサーバ）
```

外部に公開するサーバは DMZ に置き、**インターネットから社内 LAN へ直接入る通信は許可しない** のが原則です。

#### ファイアウォールのルール表の読み方

ルールは **上から順に照合し、最初に一致したルールが適用される** のが一般的です。

| 番号 | 送信元 | 宛先 | サービス | 動作 |
|---|---|---|---|---|
| 1 | インターネット | DMZ の Web サーバ | HTTPS | 許可 |
| 2 | 社内 LAN | インターネット | HTTPS | 許可 |
| 3 | すべて | すべて | すべて | 拒否 |

設問では「ルールを 1 行追加するとしたら、何番の前に入れるか」「この通信が許可されてしまう原因のルールはどれか」といった形で問われます。順番を変えると結果が変わることに注意します。

### 5. インシデント対応

#### 対応の流れ

1. **検知・報告**: 異常に気付いて、決められた窓口（CSIRT など）に報告する
2. **初動対応・封じ込め**: 感染した端末をネットワークから切り離すなどして、被害の拡大を止める
3. **調査・根絶**: ログを調べて原因と影響範囲を明らかにし、マルウェアの除去や脆弱性の修正をする
4. **復旧**: 安全を確かめてから、システムやデータを元に戻す
5. **事後対応**: 再発防止策をまとめ、関係者や必要に応じて当局（個人情報保護委員会など）に報告する

> [!CAUTION]
> マルウェアに感染した PC は <mark>**電源を切らずにネットワークから切り離す**</mark> のが原則。電源を切るとメモリ上の痕跡（実行中のプロセスや通信先）が消え、原因の調査ができなくなる。「すぐに電源を切る」は選択肢や記述でひっかけとして出る。

#### ログから読み取ること

- **認証ログ**: 短時間に多数のログイン失敗 → 総当たり攻撃。多数のアカウントに少しずつ失敗 → パスワードスプレー（リバースブルートフォース）
- **プロキシのログ**: 業務時間外に同じ外部サイトへ定期的に通信 → マルウェアが外部の指令サーバ（C&C サーバ）と通信している可能性
- **時刻の同期**: 複数の機器のログを突き合わせるには、時刻が合っている必要がある（NTP で同期する）。設問で「ログの時刻がずれていた」ことが調査を妨げた原因として問われる

### 6. 答えに使える「対策の型」

記述で対策を答えるときは、次の型に当てはめると、具体的で本文に結びついた答えにしやすくなります。

| 原因の型 | 対策の型 |
|---|---|
| パスワードが推測された・使い回された | 多要素認証の導入、パスキーへの移行 |
| 古いソフトの脆弱性を突かれた | 修正プログラムの適用、脆弱性情報の収集体制 |
| 不要な通信が許可されていた | ファイアウォールのルールを必要最小限にする |
| 感染が社内に広がった | ネットワークの区画分け、端末の検知・隔離（EDR） |
| 誰がやったか追えなかった | 共用アカウントの廃止、ログの取得と保管、時刻同期 |
| 偽の差出人のメールを信じた | DMARC の設定、利用者への教育、送金前の別経路での確認 |

## 手を動かすパート

自分が使っているメールアドレスのドメインで、SPF と DMARC の設定を DNS から確かめられます。Web 編 Chapter 2 の DNS の知識の応用です。

```bash
# Linux / macOS
dig +short TXT gmail.com          # "v=spf1 ..." が SPF
dig +short TXT _dmarc.gmail.com   # "v=DMARC1; p=..." が DMARC
```

```powershell
# Windows
nslookup -type=TXT gmail.com
nslookup -type=TXT _dmarc.gmail.com
```

DMARC の `p=` の値（`none` / `quarantine` / `reject`）が、なりすましメールの扱いの宣言です。

## つまずきポイント

> [!CAUTION]
> セキュリティの記述は **「正しいが本文と関係ない対策」** を書いてしまいがち。本文の原因に対応する対策になっているかを必ず確かめる。

- <mark>**SPF・DKIM・DMARC の役割の違い**</mark>: 送信サーバ / 署名と改ざん / From との照合と扱いの宣言
- <mark>**OAuth は認可、OpenID Connect は認証**</mark>: 名前が似ているが目的が違う
- <mark>**ファイアウォールのルールは上から順**</mark>: 最初に一致したルールで決まる
- **感染 PC は電源を切らずに切り離す**: 調査のための痕跡を残す
- **時刻同期**: ログの突き合わせの前提

## 重要な単語まとめ

| 用語 | 一言で言うと | 身近な実例 |
|---|---|---|
| **SPF** | 送ってよいサーバを DNS に登録して照合 | `v=spf1 ...` の TXT レコード |
| **DKIM** | メールの電子署名 | 改ざんの検知 |
| **DMARC** | From との一致を確かめ、失敗時の扱いを宣言 | `p=reject` |
| **パスキー** | 端末の秘密鍵でログイン | 指紋や顔でサイトにログイン |
| **OAuth 2.0 / OpenID Connect** | 許可（認可）の受け渡し / 利用者の確認（認証） | 「アクセスを許可」/「Google でログイン」 |
| **SAML** | 組織向けのシングルサインオン | 会社のアカウントで業務クラウドに入る |
| **DMZ** | 公開サーバを置く区画 | Web サーバ・メール中継 |
| **ファイアウォールのルール表** | 上から照合し、最初に一致したもので決める | 最後の行は「すべて拒否」 |
| **封じ込め** | 被害の拡大を止める初動 | 感染 PC の LAN ケーブルを抜く |
| **C&C サーバ** | マルウェアに指令を出す外部のサーバ | 定期的な不審な通信 |
| **パスワードスプレー** | 多数のアカウントに少しずつ試す攻撃 | ロックがかかりにくい |
| **EDR** | 端末の挙動を監視して攻撃を検知・隔離する | 企業の PC に入っている監視ソフト |
