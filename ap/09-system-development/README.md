## 本文

### 1. 問題の形

あるシステムの開発場面（要件の説明、設計書の一部、UML の図、テスト計画）が提示され、次のような内容が問われます。

- UML の図の **空欄**（クラス名、多重度、メッセージ）
- 要件を満たす **テストケース** や、不足しているテストの指摘
- レビューやテスト結果の数値から読み取れる **品質の状況**
- 開発の進め方（アジャイルの運用など）に関する **改善案**

### 2. UML の読み方

#### クラス図

| 表し方 | 意味 |
|---|---|
| 箱の上段・中段・下段 | クラス名・属性・操作 |
| 線の両端の `1`、`0..1`、`*`、`1..*` | 多重度（相手がいくつ対応するか。`0..1` は 0 か 1、`*` は 0 以上） |
| 白抜きの三角の矢印 | 汎化（継承）。矢印の先が親クラス |
| 白抜きのひし形 | 集約（全体と部分。部分は単独でも存在できる） |
| 黒塗りのひし形 | コンポジション（部分は全体と運命を共にする） |

**例**: 「注文 1 件には 1 個以上の注文明細がある。注文を消すと明細も消える」という関係は、注文と注文明細の間の黒塗りひし形と、明細側の多重度 `1..*` で表します。

> [!CAUTION]
> <mark>**多重度は「相手側の端」に書かれた数値を読む**</mark>。注文と明細を結ぶ線で、明細側の端に `1..*` とあれば「注文 1 件に対して明細が 1 個以上」という意味になる。自分側の端の数値と取り違えると、E-R 図の設問（AP Chapter 8）と同様に答えが逆になる。

#### シーケンス図と状態遷移図

- **シーケンス図**: 縦の点線が各オブジェクトの時間の流れ、横の矢印がメッセージ（呼び出し）を表す。時間は上から下へ進む。空欄のメッセージは、前後の矢印と本文の処理手順から埋める
- **状態遷移図（ステートマシン図）**: 状態を角の丸い四角形、遷移を矢印で表し、矢印に「イベント [条件] / 動作」を添える（AP Chapter 6 の状態遷移表と同じ内容を図にしたもの）

### 3. テストケースの設計

#### デシジョンテーブル

条件の組合せと、それぞれのときの動作を表にまとめます。

| 条件・動作 | ルール 1 | ルール 2 | ルール 3 | ルール 4 |
|---|---|---|---|---|
| 会員である | Y | Y | N | N |
| 購入額 5,000 円以上 | Y | N | Y | N |
| 送料無料 | X | ― | X | ― |
| ポイント付与 | X | X | ― | ― |

各ルール（列）が 1 つのテストケースになります。条件が n 個なら組合せは 2ⁿ 通りになるため、ありえない組合せや結果が同じものをまとめて減らします。

#### 網羅基準の上乗せ

FE で扱った命令網羅・判定条件網羅・条件網羅に加えて、AP では **判定条件／条件網羅**（判定全体と個々の条件の両方の真偽を網羅）や、`if (A and B)` を網羅するのに最低いくつのテストケースが必要かが問われます。

**例**: `if (A and B)` で判定条件網羅を満たすなら、判定が真になるケース（A＝真、B＝真）と偽になるケース（例えば A＝偽）の 2 つで足ります。一方、条件網羅は A・B それぞれが真と偽をとればよいので、(A 真, B 偽) と (A 偽, B 真) の 2 つでも満たせます（ただし、この 2 つでは判定がどちらも偽になるため、判定条件網羅は満たしません）。

### 4. レビューと品質の指標

- **バグ密度**: 見つかったバグの数 ÷ プログラムの規模（1,000 行あたりなど）。過去の実績と比べて、高すぎればテスト対象の品質が悪く、低すぎればテストが不十分である可能性があると両面から読み取る
- **信頼度成長曲線**（ゴンペルツ曲線）: テスト時間の経過とともに、見つかったバグの累計がどう増えるかを表すグラフ。<mark>**累計の伸びが緩やかになってきた（新しいバグがあまり見つからなくなった）ら、品質が安定してきたサイン**</mark>。まだ伸び続けている段階でテストを終えるのは時期尚早である
- **レビューの指摘の分類**: 設計の誤りや書式の不統一などを種類別に集計し、どの工程に問題があるかを分析する

### 5. アジャイル開発

#### スクラムの役割

| 役割 | 仕事 |
|---|---|
| **プロダクトオーナー** | 何を作るかの優先順位（プロダクトバックログ）を決め、プロダクトの価値に責任を持つ |
| **スクラムマスター** | スクラムがうまく回るように支援し、チームの障害を取り除く |
| **開発者** | スプリントの中で、動くものを作る |

#### スクラムのイベント

スプリントプランニング（何をやるか決める）→ デイリースクラム（毎日 15 分で進捗を共有する）→ スプリントレビュー（作ったものを見せて意見をもらう）→ スプリントレトロスペクティブ（進め方を振り返る）。

**ベロシティ** は、1 スプリントで完了できた作業量（ストーリーポイントの合計）です。過去の平均値から、残りの作業が何スプリントで終わるかを見積もります。

### 6. API の設計

Web 編 Ch5 で作成した REST API の設計の観点が、そのまま問われることがあります。

- リソースを URL で表し、操作を HTTP メソッドで表す（`GET /orders/42`）
- 失敗したときは、内容に合った **ステータスコード** を返す（入力の誤りは 400、権限がなければ 403、対象が存在しなければ 404）
- 同じ要求が 2 回届いても問題が起きないように **冪等** にしておく（注文の二重送信を防ぐために、要求ごとに一意な ID を付けて受け付けるなど）
- 後から項目を追加しても、古いクライアントが動かなくならないようにする（**後方互換性**）

## 手を動かすパート

デシジョンテーブルは、Python で条件の全組合せを並べて確認できます。

```python
>>> from itertools import product
>>> for member, over5000 in product([True, False], repeat=2):
...     free_shipping = over5000
...     points = member
...     print(member, over5000, "送料無料" if free_shipping else "-", "ポイント" if points else "-")
...
True True 送料無料 ポイント
True False - ポイント
False True 送料無料 -
False False - -
```

## つまずきポイント

> [!CAUTION]
> この分野は「読めば分かる」ように見えても、**図の記号の読み違い** と **テストケースの数え間違い** で失点しやすい。

- <mark>**多重度は相手側の端を読む**</mark>
- <mark>**集約とコンポジションのひし形**</mark>: 白抜きは部分が単独でも存在でき、黒塗りは全体と一緒に消える
- <mark>**条件網羅を満たしても判定条件網羅を満たすとは限らない**</mark>: 判定全体の真偽の両方が出ているかを別途確かめる
- **バグ密度が低すぎるのも要注意**: テストが不十分な可能性がある
- **プロダクトオーナーとスクラムマスター**: 何を作るかを決めるのはプロダクトオーナー

## 重要な単語まとめ

| 用語 | 一言で言うと | 身近な実例 |
|---|---|---|
| **クラス図の多重度** | 相手がいくつ対応するか | 注文 1 ― 明細 `1..*` |
| **汎化 / 集約 / コンポジション** | 継承 / 全体と部分 / 運命共同体の全体と部分 | 白抜き三角 / 白ひし形 / 黒ひし形 |
| **シーケンス図** | オブジェクト間のメッセージを時間順に表す図 | API 呼び出しの流れ |

| **判定条件／条件網羅** | 判定全体と個々の条件の真偽を両方網羅 | `if (A and B)` のテスト |

| **信頼度成長曲線** | バグの累計の伸びを表すグラフ | 伸びが緩やかになったら安定 |
